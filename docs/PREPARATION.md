# 최초 OS 준비·Wi-Fi 진단·자동 로그인

## 권장 순서

1. Rocky Linux 10 x86_64, GNOME/GDM, 일반 sudo 계정을 준비하고 ala를 설치합니다.
2. `ala config edit`에서 실제 화면 사용자를 저장합니다. DID 주소는 비워도 됩니다.
3. 새 서버의 OS 업데이트를 원하면 `ala prepare --plan`으로 변경을 조사하고 `ala prepare --apply`로 실행합니다.
4. 재부팅 대기가 나오면 직접 재부팅합니다. SSH 재접속 후 `ala prepare --apply`로 예상 커널과 상태를 확인합니다.
5. `ala setup --plan`, `ala setup --apply`로 드라이버와 기본 환경·자동 로그인·화면 정책을 적용합니다.
6. 드라이버 또는 화면 적용에 재부팅이 필요하면 다시 직접 재부팅하고 `ala check`로 확인합니다. GPU는 필요시 setup을 재실행해 컨테이너 연결까지 준비합니다.
7. 실제 모니터의 바탕화면/DID 표시와 팝업 부재를 별도로 확인합니다.

기존 서버는 초기 OS 준비를 생략할 수 있습니다. `setup`이 OS 업데이트를 강제하지 않습니다.
TUI에서는 설치·설정 화면의 **초기 OS 계획**과 **환경 설정 계획**이 다른 작업이며, 적용 확인 뒤에만 변경합니다.
`--apply --detach`는 실행 ID를 반환합니다. SSH 종료 후에도 진행하며 `ala runs list/show`, `ala logs --run RUN_ID --follow`로 다시 조회합니다.

## 업데이트 범위와 재실행

초기 OS 준비는 활성화된 Rocky 공식 baseos/appstream 및 extras/crb 저장소를 사용하며 10 계열 안에서만 갱신합니다.
기본 패키지 설치에서 사용하는 커널 변경 제한의 예외는 이 명시적 초기 준비에만 있습니다.
Chrome/Docker/NVIDIA 저장소를 통한 업그레이드, 패키지 강제 제거, 서명 우회는 하지 않습니다.
외부 NVIDIA/DKMS 모듈이 이미 있으면 커널 호환성 검토가 필요하므로 차단합니다.
계획 조회의 DNF 메타데이터는 임시 디렉터리를 사용합니다. 계획은 최종 의존성 트랜잭션 확정 내역이 아닙니다.
OS 패키지 업데이트 과정에서 서비스가 재시작될 수 있습니다.

- 패키지 변경 없음 + 실행 커널 적절: 불필요한 재부팅 없이 완료합니다.
- 패키지 변경: 현재 부팅 ID와 예상 커널을 기록하고 재부팅을 기다립니다.
- 같은 부팅에서 재실행: 업그레이드를 반복하지 않고 대기를 유지합니다.
- 새 커널 설치 후 이전 커널로 부팅: 완료 처리하지 않고 부팅 결과 확인을 요구합니다.
- 완료 후 재실행: 기록을 유지하며 전체 업데이트를 반복하지 않습니다.
- 전원 차단/실패: 자동 재개하거나 완료로 간주하지 않습니다. 현재 RPM 상태와 기록을 재조사해 명시적으로 이어갑니다.

`/var/lib/ala/prepare.json`은 작업 상태이며 사용자 구성 파일과 별개입니다. 기록을 삭제해서 정기 업데이트를 실행하지 마세요.
운영 중 자동 OS 업데이트 차단은 유지됩니다. 정기 보안 업데이트·장애 시 패키지 롤백은 별도의 유지보수 절차입니다.

## 네트워크 진단

```bash
ala doctor network
ala doctor network --json
ala doctor network --probe-url https://example.com --json
```

진단은 조회만 하며 SSID·암호를 수집하거나 연결을 변경하지 않습니다. 모듈 로딩/언로드, NetworkManager 재시작, rfkill 해제를 하지 않습니다.
정상 RPM이 있다는 사실과 실제 모듈 연결·펌웨어 초기화·IP·인터넷 통신 성공은 서로 다릅니다.
기존 설치된 드라이버가 초기화에 실패하면 반복 설치 대신 현재 부팅 로그와 전원·커널 상태를 조사합니다.
AX200의 `-110`은 초기화 timeout입니다. Windows Fast Startup은 가능한 원인 중 하나이며 모든 timeout의 원인이라고 단정하지 않습니다.
[Intel 사례](https://www.intel.com/content/www/us/en/support/articles/000059113/wireless.html)

외부 URL 요청은 명시 옵션에서만 수행하고 TLS 검증을 유지합니다. 요청 성공은 호스트 경로의 HTTP 응답이며 Wi-Fi 경로나 페이지 내용 정상 보장이 아닙니다.
사용하지 않는 Wi-Fi의 미연결은 드라이버 고장과 구분합니다. 권한·도구·로그가 없으면 확인 불가입니다.
자동 보완은 기존 setup에서 확인된 공식 누락 패키지만 대상으로 합니다. 인터넷이 없으면 유선 등 패키지 다운로드 경로를 먼저 마련해야 합니다.

## 로그인 없이 바탕화면 표시

`display=true`, `autologin=true` 및 기존 일반 사용자 지정 후 setup을 적용합니다.
자동 로그인은 로컬 화면에서 해당 사용자 권한의 접근을 허용합니다. SSH 인증/비밀번호는 유지합니다.
GNOME 첫 실행 안내, GDM 부팅 등록, 그래픽 부팅 target, 잠금/절전 정책을 준비합니다.
URL이 없어도 바탕화면에 진입하며 URL이 입력되고 autostart가 켜지면 Chrome 표시를 시작합니다.
GDM이나 현재 그래픽 세션은 강제로 재시작하지 않습니다. 적용 뒤 수동 재부팅으로 확인합니다.
[GNOME 자동 로그인](https://help.gnome.org/system-admin-guide/login-automatic.html)

`ala check`는 설정 준비·실제 세션·잠금 힌트를 분리합니다. 로그인 화면이나 세션 부재가 계속되면 현재 부팅 GDM 상태와 로그 단서를 표시합니다.
키링을 사용하는 일반 앱의 잠금 해제까지 우회하지 않습니다. 표시용 Chrome만 별도 프로필과 basic 저장 방식을 사용합니다.
BIOS 전원 복구, 부팅 전 디스크 암호 입력, 모니터 전원/케이블 장애는 이 설정으로 해결되지 않습니다.
