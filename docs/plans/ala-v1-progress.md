# ala 공개판 진행 기록

## 2026-11-10 RC38 드래그 없는 TUI 모니터 위치 변경

- 사용자가 같은 PC의 좌우·상하 배치와 출력별 사이트/콘텐츠 배정 둘 다 필요하다고 확인했다. PC 성능에 출력 역할을 고정하지 않으며, 여러 패널이 하나의 논리 출력으로 인식되는 경우는 기존 출력당 Chrome 하나를 사용한다. 서로 다른 PC는 각각 접속해 사이트를 저장/적용하는 범위이며 통합 제어를 구현한 것으로 안내하지 않는다.
- 위치 변경 버튼과 P 단축키, 기준 출력의 좌우·상하·위치 교환·정확한 좌표를 선택하는 TUI를 추가했다. 창은 초안을 복사해 편집하며 승인 전 원본과 장비를 변경하지 않는다. 반영 시 부모 초안 신원/내용과 작업 상태를 대조한다. 추가 RPC 없이 로컬 편집 후 기존 검토·적용·30초 확인/복원을 재사용한다.
- 상대 위치는 실제 논리 크기(모드·배율·회전)를 기준으로 계산한다. 세 번째 출력·모드·배율·사이트 배정을 보존하고 겹침·잘못된 기준·취소·오래된 편집 상태를 거부한다. 단일 출력은 다른 모니터를 추정하지 않는다. 기존 드래그·키보드와 설정 엔진을 제거하지 않았다.
- 모니터/TUI/저장 API 관련 98개를 통과했다. 두 개의 독립 논리 출력에 임의 사이트 조합을 저장하고 다른 대상·전체화면/배정을 보존하는 합성 검사를 포함한다. 최종 키보드 위치→검토→적용→유지를 포함한 관련 145개를 통과했다. 80×24/120×36 합성 렌더링을 생성하고 작은 화면에서 기준/방법/좌표와 취소·반영 버튼의 가시성을 직접 확인했다. 전체 CI에서 신규 통합 검사의 마지막 RPC가 반드시 submit이라고 가정한 항목이 정상 상태 polling 뒤 실패했다. 제품 코드는 바꾸지 않고 정확한 submit 횟수·payload를 확인하도록 검사만 수정한다. 최종 CI·배포 검증을 이어간다. 실제 장비·고객 구성은 변경하지 않았고 Rocky/HIWARE/비디오월 수용은 미수행이다.

- `GLOSSARY.md`에 DID 연결 PC와 표시 장치의 구분을 기록했다. 다음은 설치 시 네트워크 조건, 반복 작업 규모와 장비별 차이 확인이다. 이번 단계에서는 코드 구현·장비 변경을 수행하지 않았다.
- 조직 제공 클라우드 인스턴스를 경유해 강의실 PC에 SSH 접근하는 경계를 확인하고 `조직 접속 인스턴스`로 구분했다. 잠재적인 다수 조직·장비의 갱신 요구를 받아 Mac의 반복 접속 보조만으로 운영 요구를 충족하는지는 재검토한다.
- 기존 계획에서 제외했던 중앙 장비 관리·상태 보고와 새 요구의 차이를 확인했다. 기존 장비별 자동 업데이트와 조직 간 배포 제어를 구분하며, 외부 다운로드 가능 여부·접속 인스턴스에서의 상주 실행 허용·업데이트 대상 범위는 추가 확인한다. 중앙 관리 구조나 배포 방식은 아직 확정하지 않았다.
- 사용자는 외부 다운로드가 가능하며 CLI·프론트·애플리케이션·OS·Chrome·GPU 드라이버 전체를 갱신 대상으로 검토한다고 답했다. 이는 모든 항목의 무승인 자동 적용이나 자동 재부팅 승인과 구분한다. 조직 내 서버의 역할·상주 실행 조건은 확인 대기이며, 개별 고객 자료의 사양·접속 정보·운영 정책은 공개 저장소에 옮기지 않는다.
- 기존 코드의 자동 갱신·서명·야간 적용·실패 복구는 PC 로컬 범위임을 확인했다. 다음은 배포 승인 주체, 갱신 대상별 자동 적용 범위와 SSH 단절 시 복구 수단 확인이다.
- 사용자가 갱신 대상별 적용 정책 분리를 선택했다. CLI·프론트·애플리케이션은 검증된 버전을 허용 시간에 자동 적용하는 방향, OS·Chrome·GPU 드라이버는 변경 영향 확인 후 예약 적용하는 방향, 재부팅은 별도 허용 점검 시간으로 설계한다. 이는 설계 합의이며 기존 자동 재부팅 금지 계약을 즉시 변경하거나 장비 작업을 실행한 것이 아니다.
- SSH·부팅 장애에 사용할 별도 원격 복구 수단은 확인되지 않았다. 현장 담당자 지원 또는 방문이 필요할 수 있는 한계를 유지한다. PC 로컬 복원만으로 무인 복구를 보장하지 않는다.
- 기관에 먼저 승인 기회를 주되 장기 미적용 시 야간 자동 적용을 원하는 의도를 확인했다. 기관과 사전 합의할 적용 기한·연장/예외·점검 시간·최종 적용 권한은 아직 미결정이다. 다음 인터뷰에서 임의 적용과 사전 합의한 정책에 따른 자동 적용을 구분한다.
- 사용자가 사전 합의한 기한 이후 점검 시간에 자동 적용하는 정책을 선택했다. [ADR 0001](../adr/0001-update-approval-deadline.md)에 기관의 우선 승인·유예와 대상별 적용 조건·긴급 중지 보존을 기록했다. 구체적인 기간·연장 범위·점검 시간은 미결정이며 실제 기관 합의와 구분한다.
- 공통 관리 서비스의 필요성은 사용자도 염두에 두고 있으며 최초 조직 설치와의 개발 순서를 검토 중이다. 첫 설치 일정·완료 기준·장비 역할을 확인한 뒤 중앙 기능의 최소 범위와 도입 시점을 정한다. 코드 구현과 실제 장비 변경은 시작하지 않았다.
- 사용자가 현장 완료 작업과 원격 후속 작업, 현장 철수 기준과 최종 서비스 완료 기준을 구분하는 방향을 선택했다. 두 PC는 서로 다른 역할의 장비로 취급하며 상호 대체 가능하다고 가정하지 않는다. 실제 설치 날짜·현장 가용 시간과 PC별 워크로드는 아직 확인되지 않았고, 구체적인 철수 검사 목록은 제안 단계다.
- 최초 현장 설치 전 가능한 준비를 마치는 일정 목표를 확인했다. 두 종류의 PC 모두 Chrome 표시가 필요하며, 전체 서비스에는 마이크 STT와 CCTV 기반 분석 결과 표시가 포함된다. 이것이 각 PC에서 모든 분석을 실행한다는 뜻은 아니므로 분석 역할 배치·화면별 콘텐츠·실시간 처리 요구를 추가 확인한다. 분석 서비스의 개발·배포와 기존 장비 관리 기능을 구분하며 코드 구현은 아직 시작하지 않았다.
- 교수자 PC가 마이크 음성을 강의실 PC에 실시간 전달하고, 강의실 내부에서 STT와 CCTV 분석을 처리하려는 방향을 확인했다. 표시 화면은 복제가 아닌 개별 콘텐츠로 관리한다. 분석을 배치할 구체 장비와 지연 수치·측정 조건은 아직 확정하지 않았다.
- 인접 애플리케이션의 읽기 전용 조사에서 백엔드 실행용 컨테이너 구성과 STT·분석 스텁을 구분했다. 실제 분석 엔진의 배포 준비는 확인되지 않았으므로 CLI 설치 완료와 실제 분석 서비스 완료를 같은 결과로 판정하지 않는다. 음성 캡처·전송 경계와 분석 엔진 제공 범위를 후속 확인한다.
- 사용자가 별도 분석 서버 저장소에서 서비스를 개발·실행하고 ala는 설치·설정·실행·점검·갱신을 연결하는 경계를 선택했다. [ADR 0002](../adr/0002-separate-analysis-service.md)에 기록했다. 고사양 PC의 분석·Chrome 동시 실행은 아직 시험 후보이며 장비별 성능과 분석 엔진 구현 완료를 전제하지 않는다.
- 분석 서버의 컨테이너 이미지·Compose 배포 방식과 서비스 교체 시 설정·모델·분석 결과·저장 데이터 보존 원칙에 합의했다. 데이터 삭제는 별도 명시 작업이며, 데이터 형식 변경의 이전·복구 조건은 미결정이다.
- 사용자는 교내 관리자 화면에서도 장비·서비스를 관리할 예정이므로 ala를 유일한 관리 주체로 고정하지 않도록 정정했다. ADR 0002에 관리 창구와 실행 경로의 분리를 반영했다. 공통 실행 경로의 구체 구현과 관리자 화면의 최초 제공 범위는 아직 확정하지 않았다.
- 교내 관리자 화면은 등록된 장비 정보를 사용해 API로 제어하는 방향이며, 외부 공통 관리 서비스와 연결되지 않아도 교내 관리자 화면·현장 ala의 상태 조회와 허용된 운영을 계속 제공하는 원칙에 합의했다. API 요청 주체·기관 내부 통신 경로·인증·제어 대상과 외부 연결 복구 후 정책 충돌 처리는 후속 설계로 남긴다.
- 제어 범위는 PC·서비스 운영과 카메라 제어로 좁혔다. 사용자는 해당 API를 별도 분석 서버 저장소에서 제공할 수 있다고 보며, 어드민 백엔드 연동은 담당자에게 가이드를 인계하는 방향을 허용했다. [연동 가이드 초안](../device-management-integration.md)에 역할·요청 경로·상태/작업·권한·데이터 보존과 미결정 항목을 정리했다. 담당자에게 전송하거나 타 저장소를 수정하지 않았다.
- 사용자는 ala에서 기본 환경 준비 이후 지정 버전의 분석 서버 배포물 설치·서비스 등록·준비 상태 확인까지 연결하는 최초 설치 흐름을 선택했다. [설계 초안](ala-install-operations-plan.md)에 합의를 묶고 기존 계획의 제공 범위와 구분해 연결했다. 환경 준비와 분석 서버 대기를 구분하며, 배포물 접근 정책과 OS 설치 자동화의 우선순위는 후속 확인한다.
- 분석 서버 배포물은 회사와 설치 기관만 다운로드하도록 하는 요구를 확인했다. ala 공개 배포의 대안으로 소스 저장소와 배포 영역을 분리하고 기관·장비별 제한된 다운로드 권한을 쓰는 방식을 검토한다. 실제 가시성·배포 경로·인증 설정은 변경하지 않았다.
- 사용자가 처음 제안한 설치 방식은 설정된 OS 상태를 이미지로 복제하는 방법도 포함함을 재확인했다. OS 자동 설치와 공통 디스크 이미지 복원을 구분해 설계 초안에 추가했고, 공통 설정과 장비별 식별·자격증명을 분리하는 준비 절차를 제안했다. 이미지 제작·디스크 복원·장비 변경은 수행하지 않았다.
- 표시 담당과 분석·표시 담당의 두 장비 역할, Mac에서 장비별 설정을 준비·전달해 ala로 검토·적용하는 흐름에 합의했다. 공통 이미지와 장비별 설정을 분리하며 고정 주소 환경이라는 조건을 추가했다. OS 정적 주소와 DHCP 예약의 구분·초기 설정 주체는 미확인이다. 초기 로컬 네트워크 준비와 SSH 이후 읽기 전용 확인을 구분하며 실제 네트워크 변경은 수행하지 않았다.
- 사용자가 고정 주소를 PC의 OS에 직접 입력하는 방식임을 확인했다. 설계 초안의 미확인 항목을 정정했다. 장비별 주소는 공통 이미지와 분리하고 SSH 이전 현장 준비 항목으로 다룬다. 최초 로컬 입력·적용 자동화는 제안 단계이며 기존 네트워크 조회의 읽기 전용 계약은 유지한다.
- 사용자가 GUI에서 네트워크를 직접 설정해도 된다고 설명해 최초 로컬 네트워크 도우미 제안을 첫 구현 범위에서 제외했다. 고정 주소와 SSH를 현장에서 수동 준비한 뒤 Mac에서 ala 설치 흐름을 이어가는 기준 경로를 유지한다. 공통 이미지 검토와 장비별 역할·화면·분석 설정 준비는 유지하며 실제 네트워크 변경은 하지 않았다.
- 다음 단계 요청에 따라 현재 Config·CLI·구성 저장·작업 잠금의 경계를 확인하고 [첫 구현 계획](ala-first-implementation-plan.md)을 작성했다. 장비별 설정 준비·내보내기 → Rocky의 검토·적용 → 지정 분석 배포물 연결 → 실제 장비 수용으로 나눴다. 기존 설정 조회 응답은 구성 자체와 달라 그대로 재입력할 수 없으며, 명시적 내보내기와 신규 역할·장비 목록 경계가 필요함을 기록했다. 이번 변경은 계획 문서이며 코드·장비·원격 저장소는 변경하지 않았다.
- 사용자가 개발 시작을 보류했고, 이후 연결 모니터의 직관적 표시·좌우 순서 변경·모니터별 사이트 설정을 개발 전 요구로 추가했다. 기존 코드의 모니터 지도·식별·사이트 편집·DID 배정 교환과 OS 출력 좌표 변경을 구분해 첫 구현 계획에 기록했다. OS 배치 변경까지 필요한지는 확인 대기이며 코드 개발·장비 조작은 하지 않았다.
- 사용자가 OS가 인식하는 모니터 좌우 배치 변경도 필요하다고 확인했다. 기존 사이트 배정 교환과 별도인 신규 요구로 확정하고 용어집·첫 구현 계획에 반영했다. 식별 번호와 위치를 구분하고 변경 미리보기·적용 전 재대조·실제 배치 재검사·복원·재부팅 유지 수용을 설계 항목으로 추가했다. 좌우 배치 변경 시 사이트를 기존 출력에 유지하는 규칙은 후속 확인하며 코드 개발·실제 장비 조작은 계속 보류한다.
- 사용자가 OS 좌우 배치를 바꿔도 각 사이트는 기존 모니터에 유지하는 규칙을 선택했다. 사이트 교환은 별도 명시 작업으로 구분하고, 위치·번호만으로 재배정하지 않는 조건과 합성 수용 시나리오를 첫 구현 계획에 반영했다. 용어집도 갱신했으며 코드 개발·실제 모니터 변경은 하지 않았다. 개발 보류는 유지한다.
- 다음 단계는 개발 보류를 해제하지 않고 모니터 설정 화면 시안 검토로 진행했다. 실제 앱 소스와 분리한 대화용 시안에 합성 모니터·사이트 입력·좌우 배치·변경 검토·시안 적용·편집 취소를 표현했다. 독립 DOM 환경에서 선택·사이트 편집·모니터별 사이트 유지·검토 전 무적용·잘못된 주소 거부·취소·식별 상호작용을 확인했다. 실제 브라우저 레이아웃·CLI·Rocky·GNOME·실제 장비 수용은 검증하지 않았다.
- 사용자가 원하는 조작은 두 대의 좌우 교환 버튼이 아니라 세 대 이상·상하 배치를 포함하는 드래그앤드롭이라고 정정했다. 한정했던 요구 해석을 폐기하고 연결 출력 수에 따른 2차원 지도·경계 맞춤·클릭 편집·드래그 배치·변경 전후 도식으로 설계를 수정했다. 기존 CLI 소스·실제 장비 변경과 개발 보류는 그대로 유지한다.

## ALA-31 읽기 조사·구현 시작

- 제공된 진단에서 등록/현재 그래픽 환경은 준비됐고 GNOME의 자동 시작 진입점 호출은 확인됐다. Chrome의 지속 실행으로 이어지지 않았으며 진입점이 단계별 실패 이유를 출력하지 않아 구체 원인은 미확정이다. 사용자 저널 파일은 없었으나 시스템 저널에서 로그인 진입점 호출을 볼 수 있었다.
- 공식 systemd v257에서 reset-failed는 unloaded unit을 자동 load하지 않는다. 직전 show가 unit을 load해도 GC로 사라질 수 있으므로 항상 reset-failed를 선행하는 코드는 취약점 후보다. 반대로 loaded/inactive이면 reset은 성공하므로 fresh 상태 자체가 항상 실패한다는 가설은 기각했다. 현재 start timestamp0만으로 부팅 전체에서 실행하지 않았다고 단정한 해석도 정정했다.

- Docker의 기존 비특권/네트워크 차단/read-only 일회 이미지에 systemd/dbus가 없어 실제 user-manager GC 재현은 하지 못했다. 공식 소스·합성 경계와 실제 재현을 구분하며 불필요한 host 설치나 privileged 실행은 하지 않았다.
- 다음은 서비스 안의 제한된 준비 대기와 idempotent 로그인 연결·고정 단계 로그·UID 제한 시스템 저널 fallback을 구현한다. 현재 Chrome/GDM/장비 설정은 변경하지 않으며 실기기 원인 확정과 다음 부팅 수용은 남아 있다.

## 간편 설정의 Podman 충돌 처리

- 간편 설정 실행에서 Podman 충돌을 만나면 별도 조회 후 제거 예정 패키지를 표시한다. 기본 포커스는 취소이며 명시적 승인만 작업별 토큰으로 저장한다.
- 시스템 Python의 DNF API로 설치된 패키지와 의존성 제거 목록을 계산한다. 작업은 공통 잠금과 기존 systemd 실행 기록을 사용하며 제거 직전 사용 여부·계정·제거 목록을 재확인한다.
- 컨테이너·볼륨·이미지·pod·사용자 정의 네트워크 또는 Quadlet 설정 발견, 조회 오류, 승인 후 구성 변경, 제거 실패는 Docker 설치를 중단한다. 기존 CLI와 직접 실행 설치기의 충돌 차단은 유지한다.
- 로컬 Python 3.14 전체 회귀는 1256 passed + 56 subtests, 공개 데이터 검사와 배포 소스 포함 검사를 통과했다. 격리된 Rocky Linux 10 arm64 컨테이너에서 실제 DNF로 합성 RPM과 의존 패키지의 목록·승인 제거·재실행을 검증했다. Podman 사용 조회는 모의 검증이며 실제 장비의 사용 여부·Docker 설치 수용은 별도다.
- Python 3.12 전체 회귀도 1256 passed + 56 subtests를 통과했다. 이후 높은 UID 계정 탐색과 선행 설정 단계의 무관한 패키지 설치가 승인한 제거 목록을 무효화하지 않는 경계를 추가했고, 관련 89개 + 15 subtests를 통과했다. 실제 제거 목록이나 계정 구성이 바뀌는 경우는 계속 재승인을 요구한다.

## 화면 관리의 DID 모니터 이동

- 화면 관리의 선택 DID를 현재 출력에서 빈 출력으로 드래그하고, DID·사이트·출력 방향을 확인한 뒤 적용하는 흐름을 구현했다. 작은 터미널은 출력 행을 사용한다. 기존 설정 편집과 키보드 제어는 유지한다.
- 드롭만으로 설정을 변경하지 않는다. 승인 후 해당 DID의 출력만 저장하고 기존 설정 적용 작업으로 연결한다. 중지된 DID를 자동 시작하지 않으며, 기존 런타임의 전환·복구·공통 잠금 계약을 재사용한다.
- 다른 DID의 배정 또는 미적용 설정, 현재 작업, 출력 연결 확인 불가를 차단한다. Escape·외부/동일 출력 드롭·조회 중 구성/배치 변경·크기 변경·포커스 이탈은 마우스 캡처를 해제하고 취소한다. 건강 조회 시각만 바뀌는 갱신은 드래그를 유지한다.
- 승인 뒤에는 진행 중 조회를 기다리고 새로 조회한다. 저장 응답의 구성 스냅샷을 고정해 적용 요청에 전달하고, 서비스가 기존 변경 잠금 안에서 다시 대조한다. 다른 SSH에서 저장한 미검토 구성을 함께 적용하지 않는다.
- Python 3.12 첫 전체 회귀는 1296 passed, 4 skipped, 56 subtests를 통과했다. 이후 동시 조회 대기·저장 스냅샷 고정·다른 DID의 미적용 배정 차단을 보완했고, 최종 화면 관리·드래그·구성 대조·런타임 관련 회귀 84개를 통과했다. 실제 마우스 이벤트를 쓰는 모의 테스트와 합성 80×24/120×36 렌더링을 사용했고 실제 Rocky 검증으로 간주하지 않는다.
- 새 모듈이 배포 허용 목록에 포함되고 manifest 해시 검증을 통과했다. 공개 데이터·비밀정보 검사와 diff 검사를 수행했다. 현재 변경은 로컬 구현이며 새 PR·태그·시험판은 게시하지 않았다. 다음은 실제 Rocky의 실행/중지 DID 이동과 연결 해제 검증이다.

## 초기 안내·모니터 식별·두 화면 교환 구현

- 신규 구성의 자동 시작은 기본 켜짐이다. 간편 설정의 작업별 `initialize_displays` 선택과 생성·자동 시작 변경 확인을 추가했다. 기존 미설정 장비는 기본 미선택이며 기존 사이트·배포 연동 장비는 초기화하지 않는다.
- 설치 작업 시작 전에 로그인 fence를 기록하고, 단일 활성·잠금 해제 GNOME의 모든 확정 논리 출력에 안내 DID를 한 번만 생성한다. 주 화면의 default, 출력별 고정 ID, 복제 출력 한 대상, 최대16개를 유지한다. 준비 지연은 root 작업과 15초 timer로 이어가고, 일반 사용자 로그인은 sudo 없이 환경 import 후 시작만 보류한다.
- URL=None을 외부 요청 없는 내부 HTML 안내 모드로 지원한다. 실제 로컬 문서 로드 근거를 `waiting_configuration`/`local_page_ready`로 표시하며 사이트 정상과 구분한다. root 관리 자동 시작 등록은 설정 적용 전후에 좁게 동기화한다. 기존 실행·수동 중지·꺼짐과 미관리 파일을 보존한다.
- 모니터 식별 버튼과 GNOME47/49의 비포커스10초 표지를 추가했다. protocol1의 capabilities로 구버전을 구분하고 번호는 논리 출력 ID순으로 TUI·안내·표지에 연결한다. 연결 변경·잠금·확장 종료 시 표지를 정리한다.
- 목적 출력에 전체화면 DID 하나가 있으면 두 화면 교환 확인을 제공한다. 서버의 영속 작업 하나가 두 출력만 교환하며 committed/desired 코드와 다른 설정은 보존한다. commit 결정 전은 이전 배정 복구, 결정 후는 새 배정 정리로 처리한다. lease만료·부팅 후에도 미완료 journal의 격리를 유지하고 수동 중지·조회 불가·부분 예약·복구 실패를 구분한다.
- 실제 leaf 제어·환경 pin·사용자 구성 로드·Chrome 종료 후조건을 잇는 모의 통합을 포함했다. 등록 충돌의 실제 이유와 조치를 숨기지 않으며 불완전 초기 준비의 로그인 fence는 유지한다. 영속 교환 결과에 맞춰 TUI 접수/완료/복구 상태를 갱신한다.
- Python3.12 전체 회귀 1514 passed, 4 skipped, 56 subtests를 통과했다. 이후 좁은 UI 추적 정리와80×24 대상 행 노출 보완 후 관련71개를 통과했다. Bash/Node 구문, 공개 데이터·비밀정보, 배포88개 manifest 해시·새 모듈·기능 metadata 포함 검증을 통과했다.
- 합성80×24/120×36 TUI를 렌더링하고80×24 실제 보이는 대상 행과 키보드 선택을 확인했다. 로컬 Mac의 격리된 Chrome 임시 프로필에서 안내 HTML을 렌더링했다. 이는 실제 Rocky GNOME·패널·부팅 검증을 대체하지 않는다.
- 실제 장비 검증은 미수행이다. 이 채팅에는 앱 터미널 세션이 없고 열린 터미널 앱의 도구 접근도 제한되어 원격 장비를 변경하지 않았다. 새 PR·태그·프리릴리스를 게시하지 않았으며 기존 RC26은 불변이다. 후속은 새 배포 후보의 CI와 시험 장비에서 초기 안내→식별→사이트 적용→교환→재부팅 수용이다.

## 모니터 중심 화면 관리 개편

- 화면 관리의 표시 대상 표와 메인 운영 버튼을 제거했다. 모니터 클릭·방향키·Enter로 해당 DID 설정을 열고, 시작·중지·재시작·페이지 새로고침·로그·배포 재시도·교환 복구는 설정 창 안에서 사용한다. 메인에는 모니터 식별과 다시 조회만 유지한다.
- 연결 해제·미배정·출력 확인 불가 대상은 접힌 별도 영역에서 계속 열 수 있고 화면 추가도 제공한다. 한 모니터에 여러 분할 DID가 있으면 명시적으로 대상을 선택한다. 빈 확정 출력은 출력이 미리 선택된 추가 창만 열며 저장 전에는 변경하지 않는다.
- 모니터는 26×7 셀의 테두리·받침대가 있는 고정 모양이다. 해상도는 문자로 표시하고 공간이 부족하면 줄바꿈·스크롤한다. 논리 출력 ID순 번호는 식별 기능과 일치하며, 키보드 선택에 따라 상단 상태도 같은 DID를 따라간다.
- 클릭과 2셀 이상 드래그를 구분하고 취소·무효 드래그가 설정 열기로 이어지지 않게 했다. 기존 단일 이동·영속 교환 작업, 승인 전 무변경, 승인 뒤 구성·출력·상대 재검사와 적용 스냅샷 고정을 보존한다.
- 운영 가능 조건을 대상별 공통 함수로 분리했다. 열린 설정 창의 DID ID와 적용 구성 스냅샷을 고정하고, 주기 조회에서도 편집 값과 포커스를 보존한다. 미저장 편집 중에는 로그 외 운영을 차단한다. 빠른 점검에서 같은 DID의 설정 창으로 연결하되, 느린 조회를 기다리다 다른 화면으로 이동하면 뒤늦게 창을 열지 않는다.
- Python 3.12 전체 회귀는 1563 passed, 4 skipped, 56 subtests passed였다. 이후 초기 포커스·파스텔 접힘/스크롤 색·키보드 선택 상태를 보완한 최종 코드에서 지도·드래그·화면 관리·빠른 점검 연결 회귀 92개를 통과했다. 합성 80×24·120×36 컬러 렌더링으로 고정 모양, 운영 메뉴 노출과 저장/닫기 버튼을 확인했다.
- 변경 파일 공개 데이터·비밀정보 검사, diff 검사와 고정 wheel을 사용하는 로컬 배포 묶음을 검증했다. 네 TUI 모듈이 묶음에 최종 소스와 동일하게 포함된다. 실제 Rocky 장비 변경·수용과 PR·태그·새 프리릴리스는 수행하지 않았으며 게시된 릴리스는 유지한다.

## 모니터 식별 안내와 DID 상태 분리

- RC28 사용자 환경에서 구버전 확장 기능 안내가 나타났고, 사용자가 장비 재부팅 뒤 모니터 식별이 동작한다고 보고했다. 실행 중 GNOME 확장 코드와 CLI·설치 파일의 갱신 시점이 다른 경우로 판단한다. 이는 사용자 관찰이며 도구로 실제 GNOME·패널·세션을 검증한 결과와 구분한다.
- 식별 응답이 선택 DID의 Chrome 결과에 저장되어 Chrome 실행 실패와 합쳐지고, 응답의 재로그인 안내가 가려지는 TUI 문제를 합성 환경에서 재현했다. 식별 결과·진행·다음 행동을 세션 알림으로 분리하고 기존 DID 상태·로그·진행 기록은 보존했다. 선택 변경·주기 조회에도 알림을 유지하며 명시적 조회나 다음 운영 요청에서 정리한다.
- 식별 실패 시 일괄 간편 설정을 바로 권하지 않고 먼저 확장 파일 상태를 확인하도록 안내한다. 현재 CLI는 시스템 확장 파일을 갱신하지 않으며 확장 파일 반영과 GNOME 재로그인은 별도 단계다. 파일 두 항목의 읽기 전용 확인과 최신·갱신 필요·확인 불가별 조치를 화면 가이드에 추가했다. SSH 재접속과 GNOME 재로그인을 구분한다.
- Python 3.12 식별·GNOME·API 회귀 79개, 신규 식별 TUI 회귀 20개, 기존 화면 관리·드래그·빠른 점검 연결 회귀 70개를 통과했다. 80×24·120×36에서 식별 결과와 Chrome 상태 분리, 재로그인 조치 노출, 기존 대상 제어와 기록 보존을 모의 검증했다. 변경 파일 공개 데이터·비밀정보와 diff 검사를 수행했다.
- 수정은 로컬 상태이며 새 PR·커밋·태그·프리릴리스를 게시하지 않았다. RC28 배포물과 실제 장비는 변경하지 않았다.

## RC29 작업 공간·모니터 배치 후보

- 사용자가 발견한 가상 데스크톱은 GNOME 작업 공간으로 구분했다. DID 계정의 동적 작업 공간을 끄고 수를 하나로 준비하며, DID 자동 시작 로그인 경로에서도 같은 사용자 설정을 확인한다. 다른 계정이나 전역 잠금은 변경하지 않는다. 두 키의 쓰기 가능 여부를 먼저 확인하고 저장 뒤 재검사하며, 실제 사용자 bus가 없으면 보류한다. 상태 조회는 읽기 전용이다.
- 배치 정상 판정은 실제 사각형·전체화면·현재 작업 공간 소속을 모두 요구한다. 다른 공간의 관리 창 하나만 현재 공간으로 옮기며 현재 작업 공간을 강제 전환하지 않는다. 확장에 관측 기능이 없으면 적용을 안내하고, 새 후보의 실행 중 전환은 기존 창을 중지하기 전에 기능 지원을 확인한다. 중지 DID의 코드 선택은 기존 실행 미검증 계약과 수동 중지를 유지한다.
- GNOME 47·49 공식 소스와 지연된 창 구성 응답 모의 환경에서 이전의 연속 이동·전체화면 요청이 목적 출력 반영을 기다리지 않는 취약점을 확인했다. 새 구현은 목적 출력 실제 반영 뒤 전체화면으로 진행하고, 이미 맞는 창은 변경하지 않는다. 출력·구성·창·프로세스·세션·작업 공간 변경과 사용자의 창 드래그에는 후속 조작을 취소한다. 다른 창과 연결된 대상은 함께 이동할 위험이 있어 차단한다. 이 결과만으로 사용자 장비의 두 창 동시 이동 원인을 확정하지 않는다.
- 모니터 카드·상세에는 물리 모드와 배율, 불명확할 때 논리 영역임을 표시한다. 저장 배정과 적용된 설정의 배정을 분리하고 거부된 드래그의 이유를 해당 대상에 표시한다. OS의 모니터 좌표·해상도·배율을 편집하는 기능은 추가하지 않았다.
- 관련 통합 회귀 162개와 별도 코드 전환 사전 검사 리뷰 26개를 통과했다. 80×24·120×36 모의 렌더링을 직접 확인했으며 Bash 14개·확장 구문, 변경 파일 공개 검사와 고정 wheel 배포 빌드·manifest 88개·진입점 버전 한 줄을 확인했다. 새 RC29 후보의 전체 Python 3.12 검증과 CI·게시 검증을 이어간다.
- 현재 실제 장비·Chrome·GDM은 조작하지 않았다. 멈춘 장비의 PID 0을 실행 실패의 근거로 삼지 않으며, CLI 버전과 DID 선택 버전의 차이도 의도된 분리로 다룬다. 설치 파일 반영 → GNOME 재로그인 → DID별 화면 코드 적용 → 명시적 시작·실제 표시 확인 절차를 화면 가이드에 추가했다.
- 마지막 전체 로컬 회귀는 1735 passed, 4 skipped, 56 subtests와 간편 설정 하위 항목 기대값 1개 실패였다. 기존 3개 설정 항목에 새 작업 공간 항목을 포함하고, 해당 정책의 변경 필요 상태가 구성 전용 조회에도 노출되는지 검사하도록 보완했다. 프로덕션 코드는 이 실행 뒤 바꾸지 않았다. 최종 전체 통과는 정확한 커밋의 CI로 확인한다.
- 관련 재검사 58개와 index 전체 공개 검사를 통과해 PR #19를 열었다. GNOME 47·49 공식 소스 추가 리뷰에서 작업 공간 수 축소 시 GNOME 자체가 창을 합치고 제거되는 활성 공간을 전환할 수 있음을 확인했다. 직접 작업 공간을 활성화하지 않는다는 설명을 개별 창 배치 API에 한정하도록 문서를 보완했다. 두 CI 경로의 실제 Linux Chrome 검사는 통과했으며 전체 회귀를 계속 확인한다.

- 브라우저 프로필·계정·설치 패키지·자동 운영 정책은 보존하고, 기존 사이트·출력·자동 시작·프론트 연동의 변경을 사전 검토하도록 계획했다. 코드 구현·장비 초기화·PR·릴리스는 수행하지 않았다.

## DID 전체 초기화 구현·통합 검증

- 승인한 계획에 따라 `display_reset` 전용 모듈과 preview/submit/status/recover API, root 고정 worker·부팅 복구 service·제한된 로그인 대기 timer를 추가했다. 기존 안내 준비의 보호 조건을 완화하지 않고 후보 생성 함수를 재사용한다.
- 중지 전 구성·확정/후보 선택·세대·실행 의도·관리 unit/자동 시작 등록을 관리자 전용 기록에 백업하고 해시를 재검증한다. 전역 영속 보호 기록을 대상별 시작·프론트/런타임 전환·설정 저장·설치에 연결했다. commit 전에는 이전 배정, 이후에는 새 배정으로 복구한다. 새 수동 중지는 우선하고, 제외 대상의 프로필·코드 참조는 보존하며 자동 실행에서 제외한다.
- 화면 관리의 스크롤 영역 안에 접힌 관리 도구·취소 기본 확인창·진행/기록/백업 위치·명시 복구를 추가했다. 선택 DID의 Chrome 결과와 전역 초기화 결과를 분리하며, 완료 후 편집 구성을 다시 조회한다. 계정·OS·패키지·프로필·자동 운영 정책과 게시된 RC29는 변경하지 않았다.
- 중간 Python 3.12 전체는 1752 passed 및 1760 passed(각 4 skipped, 56 subtests), 관련 최종 회귀 83개를 통과했다. 이후 부팅 복구의 GNOME 대기·원래 실행 의도 재개·10분 대기 상한과 완료/실패 후 timer 해제를 보완하고, 이 최종 코드의 전체 회귀·배포 검증을 진행한다. 모의 검증과 실제 Rocky GNOME·모니터·재부팅 수용은 구분한다.
- 실제 장비 초기화·SSH 제어·PR·병합·새 릴리스는 수행하지 않았다. 로컬 기능을 검증한 뒤 설치된 시험 장비에서 확인창 취소 → 초기화 → 안내·식별 → 사이트 재설정 → 재부팅 수용을 별도로 진행해야 한다.

- 로그인 대기·실행 재개 보완 후 Python 3.12 전체 회귀는 1768 passed, 4 skipped, 56 subtests passed(356.54초)였다. 4 skipped는 별도 Linux Chrome 실환경 검사이며 실제 Rocky 수용으로 대체하지 않는다. 이후 기록 구조·프로토콜 형식 검증을 보강한 전용 32개가 통과했고, 타이머 해제 실패를 구성 확정과 분리하는 마지막 표시 보완의 핵심 통합 회귀를 재검증한다.
- 실제 마우스/키보드 모의 이벤트로 80×24·120×36 취소 기본 확인창·명시 승인·재접속 상태 조회를 확인하고 두 크기 렌더링을 직접 검토했다. 공개 데이터·비밀정보 검사, Bash/GNOME 확장 구문, 로컬 후보 manifest 89개 해시·새 모듈/문서의 소스 일치·display_reset_protocol 표기·격리된 버전 한 줄 응답을 확인했다. 로컬 후보만 생성했고 게시된 RC29 자산은 변경하지 않았다.

- 마지막 보완(기록 구조 검증·서비스 확인 불가·타이머 해제 실패 표시)을 포함한 초기화/TUI/직접 설치/화면 관리/교환/런타임/업데이트/새로고침 핵심 회귀 157개를 통과했다(37.73초). 전체 1768개 결과와 이 최종 보완 재검증을 구분해 기록한다. 모든 변경 파일의 공개 데이터·비밀정보 및 diff 검사와 배포 후보의 소스 일치를 다시 확인한다.
