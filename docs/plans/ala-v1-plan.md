# ala 공개판 계획

## 제공 범위

Rocky Linux 10 x86_64 + GNOME/GDM 환경에서 기존 일반 사용자를 대상으로 설치·설정·검사·Chrome 표시를 관리한다.
Python 3.12, argparse, Textual과 내부 Bash 모듈을 사용한다.
OS 설치·파티션·애플리케이션 배포·DB 운영·DID 패널 제어는 제외한다.

## 유지할 계약

- 현재 상태 조사 → 변경 계획 → 적용 → 재검사. 이미 정상인 패키지와 동일 설정은 유지한다.
- plan/check/status는 설치·서비스 변경·설정·백업 생성을 하지 않는다.
- root 고정 실행기와 systemd 작업은 SSH 종료와 독립한다. 설치·갱신은 같은 잠금을 사용한다.
- 기존 구성·Chrome 프로필·Docker 설정을 보존한다. 실행 중 서비스 강제 재시작이나 자동 재부팅은 하지 않는다.
- 새 표시 프로필, 일반 사용자 Chrome, GNOME 자동 로그인·잠금/절전 방지, F11 전체화면을 사용한다.
- 표시용 Chrome만 --password-store=basic을 사용한다. 이 프로필에 인증정보를 저장하지 않는다.
- setup은 전체 OS 업데이트를 하지 않는다. prepare는 별도 최초 공식 OS 준비와 명시적 재부팅 검증이다.
- NVIDIA 및 공식 드라이버 누락을 조사한다. 미지원·초기화 실패를 자동 패키지 삭제/보안 우회로 해결하지 않는다.
- 네트워크 진단은 연결을 변경하지 않는다. 외부 probe는 명시 옵션이며 호스트 통신과 Wi-Fi 통신을 구분한다.
- 실제 화면 관찰을 프로세스 인자·모의 테스트로 대체하지 않는다.

## 공개 배포 준비

1. 공개 코드·문서·테스트를 유지하고, 원래 개발 이력은 민감한 내용을 정리해 작성자·날짜·병합 관계를 보존한 채 연결한다.
2. 인증 없는 HTTPS 다운로드·설치·수동 갱신 절차를 문서화한다.
3. 기존 버전은 덮어쓰지 않고 새 후보를 빌드·검증·게시한다.
4. CPU/GPU 실기기 수용 후 정식 버전을 판단한다.

## 후속 제안 — 아직 미구현

주기적 업데이트 타이머, 배포 서명 검증, 단계적 배포, 장비 상태 보고는 별도 구현 대상이다.
공개 다운로드가 가능하다는 사실을 자동 업데이트가 구현되었다는 의미로 설명하지 않는다.

## 검증

읽기 전용·멱등성·권한 분리·설치 잠금·실행 기록·GPU/네트워크 진단·TUI·배포 설치 회귀를 유지한다.
실제 장비에서 첫 적용 → 재실행 → SSH 재접속 → 재부팅 → 화면·GPU 수용을 별도로 수행한다.

## ALA-13 — 목적 중심 첫 화면과 순서형 설정

- 첫 화면은 처음 설정/현재 설정 보완, 서버 상태 확인, 화면 관리, 고급 설정 네 진입점으로 줄인다.
- 순서형 설정: 기존 계정 확인 → 바탕화면/DID 선택 → 필요한 변경 요약 → 명시적 설정 시작 → 진행/다음 행동.
- sudo는 시작 동선에서 처리하고 암호는 sudo가 직접 받는다. 기존 고급 구성·OS 준비·실행 기록은 고급 설정 아래 유지한다.
- 저장된 선택 옵션을 보존하며 계획 판정·구성 변경 감지·단일 작업·백그라운드 실행 계약을 재사용한다. 사용자에게 plan/apply 개념을 요구하지 않는다.
- 80×24 키보드 흐름, 취소/실패/중복/계획 불일치/재접속을 headless 테스트한다. 기존 CLI/설치 엔진 회귀도 유지한다. RC4를 덮어쓰지 않고 새 RC5로 준비한다.

## ALA-14 — 새 버전 안내·명시적 자체 갱신

- 시작 화면에서 비동기 읽기 전용 업데이트 조회. 실패해도 환경 관리를 막지 않는다.
- ala update --check [--json], ala update [--prerelease]. 기본은 정식판, 시험판은 명시 선택. 버전 숫자 비교로 다운그레이드 방지.
- 공개 GitHub API와 고정 저장소 자산만 사용하며 인증정보를 요구/저장하지 않는다. HTTPS와 SHA-256·manifest 검증. 이는 서명 검증과 다르다.
- root 고정 실행기가 systemd 작업으로 갱신하여 SSH 종료와 분리한다. 기존 installer의 잠금·원자적 current 전환·구성 보존을 재사용한다.
- RC5는 불변. 기능 포함 버전으로 최초 수동 갱신 필요. 자동 적용·정기 타이머는 범위 밖.

## ALA-15 — 가독성·차단 원인 우선 화면

- 차단 상태와 재부팅 등 적용 대기를 분리한다. 차단 패키지·실제 상태·다음 조치를 숨기지 않는다.
- 차분한 색상, 상태 카드, 명확한 포커스, 접는 상세 내역으로 정보 밀도를 줄인다. 80×24에서도 키보드로 접근 가능해야 한다.
- Podman 차단은 Docker 공식 RHEL 설치 안내에 근거해 유지하며 자동 삭제하지 않는다. 기존 일반 사용자/root 컨테이너·볼륨 점검 절차를 안내한다.
- 모의 Podman 화면·정상 화면을 렌더링하고 키보드·회귀 테스트 후 RC7 후보로 제공한다.

## ALA-16 — 단계별 집중형 화면

- 사용자 선택: 가운데 작업 메뉴, 한 화면에 한 작업. 기존 왼쪽 고정 메뉴를 제거한다.
- 홈은 작업 이름+설명 목록, 설정은 계정/화면/확인의 진행 표시와 고정된 이전/다음 버튼을 사용한다.
- Esc/상단 홈으로 언제든 작업 목록에 돌아가며, 상세 화면으로 전환하면 해당 내용에 포커스를 둔다.
- 80×24/120×36, 크기 변경, 차단/정상/작업 진행, 키보드와 무색 터미널을 검증한다.
- 설치 엔진·명시적 적용·단일 변경 작업·구성 보존 계약 유지. RC8 후보로 준비한다.

## ALA-17 — 실행 시 관리자 인증

- 사용자 결정: 설치·설정에 필요한 관리자 권한으로 실행되도록 한다. 대화형 ala 시작에서 sudo 인증 후 전체 관리 화면을 root로 실행한다.
- 검증된 설치 릴리스의 고정 Python/entry를 재실행하며 현재 버전에 고정한다. 소스 폴더를 자동 승격하지 않는다.
- help/version/update --check는 인증 없이 유지한다. 비대화형 CLI는 기존 sudo -n 관리자 RPC를 유지해 암호 입력으로 멈추지 않는다.
- sudo ala도 지원한다. 화면 계정은 저장된 일반 사용자 또는 원래 sudo 사용자를 사용하며 Chrome/user service는 일반 사용자로 유지한다.
- 디자인 추가 변경은 사용자의 구체적 불편·참고 방향을 확인한 뒤 결정한다. 이 단계에서는 임의의 새 테마를 추가하지 않는다.

## ALA-18 — 간편 설정·상태 확인만 기본 제공

- 최신 사용자 결정: 원래 setup-base.sh처럼 간편 설정 한 번과 의도한 상태 검사면 충분하다. 기본 전체화면/여러 단계 TUI를 일반 터미널의 짧은 진입 화면으로 대체한다.
- 기본 ala: Enter 간편 설정, s 상태 확인, q 종료. 관리자 인증 후 저장된 설정을 재사용하며 처음이면 sudo 실행자의 일반 계정과 기본값을 사용한다.
- 간편 설정은 기존 submit/설치 엔진으로 한 번에 적용한다. 작업별 실제 상태를 재검사하고 위험한 패키지 삭제 등은 기존 엔진에서 차단한다.
- 최초 적용 때만 검증한 기본 구성을 공통 잠금 안에서 저장한다. 조회는 저장하지 않으며 기존 구성은 덮어쓰지 않는다.
- 상태는 기능별 정상/변경 필요/적용 대기/확인 불가를 요약하고 문제의 실제값·다음 조치를 보여준다. 전체 JSON은 유지한다.
- 기존 TUI는 ala tui 및 명시적 상세 명령으로만 접근한다. 재부팅/전체 OS 준비는 기존 명시적 작업을 유지한다.
- ALA-16의 기본 집중형 전체화면 결정을 이 결정으로 대체한다. RC9 후보에 관리자 진입과 간편 흐름을 함께 반영한다.

## ALA-19 — TUI 유지, 두 화면으로 단순화

- 사용자 정정: TUI는 필요하고 기존 네 메뉴가 과했다. ALA-18의 기본 텍스트 화면 결정을 기본 TUI로 되돌린다.
- ala / ala tui는 간편 설정과 상태 확인 두 화면만 제공한다. 다단계 wizard 없이 저장된 구성 또는 기본 계정으로 간편 설정 버튼 한 번에 submit한다.
- 초기 조회와 상태 화면은 읽기 전용이다. 기존 root 진입·공통 잠금·첫 구성 저장·작업 지속·단계별 엔진 차단은 유지한다.
- 진행 중 작업 재접속/중복 실행 차단/기능별 상태·원인·다음 조치/키보드·80×24를 검증한다. 상세 JSON과 명시적 기존 명령은 유지하고 텍스트 콘솔은 ala console로 선택한다.
- Podman을 자동 삭제하지 않는다. 정확한 조회 명령과 직접 제거 전 검토 절차를 안내하며 폐기된 '이전→변경 확인' 문구를 기본 흐름에서 제거한다.
- 담당 분리: 두 화면 TUI+테스트, Podman 판단 읽기 전용 검토를 에이전트에 위임. 주담당은 CLI 통합·문서·공개 검사·CI·RC10 후보.

## ALA-20 — 설치 항목별 현재 진행 상태

- 간편 설정에도 기능별 표를 제공한다. 이벤트 이력 누적 대신 항목별 마지막 상태를 한 행에서 갱신한다.
- 완료/정상 유지 초록, 진행 중 청록, 대기 노랑 또는 회색, 차단/실패 빨강으로 표시하며 한국어 라벨·기호를 함께 쓴다. kept 원문을 표시하지 않는다.
- 아직 실행하지 않은 단계는 대기/미실행으로 표시한다. 스크립트 완료 이벤트보다 최종 검사 불일치·재부팅 대기를 우선하며 진단 실패 원인을 숨기지 않는다.
- 상태 표는 선택·스크롤 위치를 유지하고 실행 중 단계는 사용자가 상세를 탐색하지 않을 때 따라간다. 선택한 항목의 원인·다음 조치를 하단에 표시한다.
- 설치 엔진·작업 기록 포맷은 바꾸지 않는다. 순수 상태 투영 모델과 UI 통합을 분담하고 모의 진행/재접속/최종 결과를 검증한다. RC11 후보로 준비한다.

## ALA-21 — 큰 기능 안의 세부 설정 표시

- 사용자가 큰 기능 내부의 구성 항목과 어떤 설정을 처리하는지 보기를 요청했다. 기본 두 탭은 유지한다.
- 큰 기능 행에 실제 진행 중인 세부 작업을 표시하고 Enter로 해당 기능의 세부 항목을 펼쳐 상태를 확인한다. 상태/색상은 기존 계약을 재사용한다.
- 정적 카탈로그는 실제 스크립트·검사 ID와 매핑한다. 실행 중이라는 판정은 추측하지 않고 구조화된 substep 신호가 있을 때만 표시한다.
- Shell은 opt-in 구조화 마커를 기존 명령 앞뒤에서 보고한다. root worker는 허용 ID/state만 additive substeps 기록에 저장한다. 일반 로그의 문장을 상태로 추측 파싱하지 않는다.
- 원래 스크립트의 명령·실패·종료·보안 정책을 유지한다. 기존 실행 기록에 세부 신호가 없으면 확인 전으로 표시하고 재접속/최종 검증/미실행을 구분한다.
- 카탈로그/순수 모델과 Shell 마커를 분담하고 주담당은 스트리밍·worker·TUI·통합·RC12 후보를 관리한다.

## ALA-22 — TUI 여백과 반응형 배치

- RC12 사용 화면에서 버튼·설정 요약·진행 표가 붙고 긴 항목이 잘리는 문제를 개선한다. 기본 두 탭과 기존 실행 흐름을 유지한다.
- 계정/표시 정보와 실행 버튼을 툴바로 묶고, 작업 요약·진행 표·선택 상세 사이 간격과 제목을 분리한다. 넓은 화면에서는 내용 최대 폭과 열 폭을 늘린다.
- 80×24는 압축 배치를 사용하며 더 높은 화면은 상하 여백과 행 간격을 늘린다. 상세·버튼·하단 키 안내는 화면 안에 유지하고 표는 스크롤로 탐색한다.
- 상태 의미/설치 엔진/실제 장비 설정은 바꾸지 않는다. 레이아웃 검증을 분담하고 실제 Textual 합성 화면을 여러 크기로 렌더링한다.
- 새 RC13 후보로 제공하며 RC12 파일은 변경하지 않는다.

## ALA-23 — 상태 조회 지연과 화면 구분

- Rust 재작성에 앞서 실제 병목인 외부 명령의 직렬 대기·동일 조회 반복을 줄인다. 실제 서버 성능은 별도 측정하며 모의 수치를 실제 개선율로 주장하지 않는다.
- 읽기 전용 status/inspect/plan의 독립 검사는 제한된 병렬 실행과 조회 한 번 안의 동일 명령 공유를 사용한다. 설치 전후 재검사와 변경 실행은 캐시를 공유하지 않는다. 실패·권한·시간 초과 판정과 결과 순서는 유지한다.
- 상태 JSON에 검사별 소요 시간과 전체 시간을 추가해 장비에서 병목을 확인할 수 있게 한다. 설정·실행 중 작업 정보는 전체 검사 완료를 기다리지 않고 먼저 표시한다.
- 두 탭은 유지하고 설정 대상/현재 작업/검사 결과/선택 상세를 표면·제목·강조로 구분한다. 부모와 자식 계층을 강화하고 최초 조회 중·갱신 중을 표시한다.
- 세부 기록 없음과 실제 조회 실패를 표시 이유로 구분하며 원래 CheckResult 판정과 종료 코드는 유지한다. 정상 집계는 합쳐 조치·적용 대기를 구분하기 쉽게 한다.
- 성능/읽기 전용 검증과 TUI/이유 표시 검증을 분담한다. RC14 후보로 준비하며 기존 RC13 파일은 유지한다.

## ALA-24 — Chrome 자동 등록·현재 세션 시작 보완

- 사용자가 간편 설정 완료 후에도 Chrome 자동 시작 등록이 설정 필요, 실행 확인이 적용 대기라고 보고했다. 실제 장비 SSH 조회는 연결 거절로 확인하지 못했으며 진단 문구를 기다린다. 모의 코드 재현과 실제 원인은 구분한다.
- unit/desktop 파일은 버전별 RELEASE 경로 대신 설치기의 고정 `/usr/local/bin/ala` 진입점을 사용한다. 첫 명시적 setup에서 기존 ala 관리 파일만 백업·이전한다. 이후 도구 버전만 바뀌어도 등록 불일치가 생기지 않게 한다.
- setup은 등록 후 URL·단일 활성 그래픽 세션·user manager 환경이 준비된 경우 중지된 새 ala Chrome의 시작까지 처리한다. 정상 실행·기존 did-chrome·외부 프로필 사용·실패 제한 상태를 강제 재시작하지 않는다. root Chrome/DISPLAY 추정/GDM 강제 재시작/자동 재부팅은 금지한다.
- 화면 정책·Chrome 등록은 기본 환경/업데이트 안전 검사/장치/셸/SSH 다음, Docker/GPU보다 먼저 직렬 적용한다. Docker/GPU 차단 때문에 등록을 놓치지 않게 하며 원래 오류와 종료 코드는 보존한다. 일반 DAG·설치 병렬화는 이번 범위가 아니다.
- 적용 대기는 원인·다음 행동을 우선 표시한다. 재로그인/사이트 응답 대기 등 외부 조건과 자동 등록 미적용을 구분한다. 조회는 설정하지 않는다.
- display/engine/표시 개선을 분담해 회귀·멱등성·일반 사용자·구버전 등록 이전을 검증한다. RC15 후보로 준비하며 RC14 파일은 변경하지 않는다.
