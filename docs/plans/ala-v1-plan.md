# ala v1 구현 계획 — 승인 기준

승인일: 2026-10-29. 이 문서는 사용자가 승인한 계획의 실행 기준이다.
프로젝트: `ubion-dev/project-ai-learning-analytics-instance-setup` (비공개), 명령: `ala`.

### 승인 후 추가 지시

2026-10-29 사용자는 두 장비가 아직 세팅 전이므로 자유롭게 설치·테스트해도 된다고 명시했다.
기존의 유지보수 시간 확인 조건은 이 지시로 해제한다. 다만 잘못된 장비에 작업하지 않도록 실제 CPU/GPU 접속 대상과 기기 식별은 먼저 확인한다.

2026-10-29 추가 요청: 초기 설정에서 필요한 장치 드라이버를 자동 준비한다(ALA-08).
Linux 커널의 기존 드라이버는 보존하고, PCI/USB 장치와 연결된 드라이버를 조사해 확인된 공식 펌웨어와 실행 커널에 정확히 맞는 모듈의 누락만 보완한다.
NVIDIA 전용 경로는 유지한다. 미지원 장치·저장소 장애·권한 부족은 정상으로 숨기지 않는다.
네트워크/그래픽 드라이버를 언로드하거나 NetworkManager를 재시작하지 않고 적용에 재부팅이 필요하면 대기로 남긴다.
설치 의존성 때문에 새 부팅 커널이나 Rocky release 패키지가 따라오는 작업은 차단한다. 일반 의존성 패키지까지 동결한다는 뜻은 아니다.
임의 웹 검색 결과의 드라이버·.run 설치·BIOS 업데이트는 포함하지 않는다. RC1은 보존하고 변경 코드는 RC2 후보로 검증한다.
PCI 저장·오디오와 USB 복합 장치의 모든 인터페이스에 driver binding을 강제하지 않는다. 이들은 정보 조사만 하고, 일반 모듈 자동 보완은 네트워크·그래픽 및 명확한 USB 네트워크 인터페이스로 제한한다.
하드웨어 지원 미확인 자체는 독립적인 셸·Docker·화면 정책 적용을 막지 않지만 최종 결과에는 남긴다. 실제 RPM 설치 실패는 이후 적용을 중단한다.

## 목표와 범위

SSH로 접속한 Rocky Linux 10 x86_64 서버 한 대의 설치·설정·검증·Chrome 관리를 수행하고, OS 정상 부팅 후 DID 화면을 사람의 입력 없이 복구한다.
GNOME/GDM과 기존 일반 사용자가 준비된 환경을 지원한다. CPU/GPU 서버에 같은 도구를 설치한다.
Python 3.12, argparse, Textual과 기존 Bash 설치 기능을 사용한다.
BIOS 전원 복구, 부팅 전 디스크 암호, OS 설치·파티션, 앱 배포, DB 운영, 사이트 인증, DID 제어 장비·패널 배치, 다중 서버 원격 실행은 제외한다.
Alibaba 자동 호출과 전역 플러그인 변경은 하지 않는다.

## 사용자 결정

- Linux 화면 계정은 기존 일반 사용자를 재사용한다.
- 기존 Chrome와 chrome-did 프로필은 보관하고 복사·변환·삭제하지 않는다.
- DID는 로그인 없는 HTTP/HTTPS 페이지이며 새 `~/.config/ala/chrome-display` 프로필을 사용한다.
- 완전 무인을 위해 표시용 Chrome에만 `--password-store=basic`을 적용한다. 이 프로필에 인증정보를 저장하지 않는다. 키링을 사용하는 저장 방식보다 보호가 약함을 문서화한다.
- GNOME 자동 로그인, Chrome 부팅 자동 시작·비정상 종료 복구까지 포함한다.
- TUI는 화살표·Tab·Enter·Space·Esc·q로 제어하며 80×24 기준, 작은 터미널 안내를 제공한다.
- 기본 패키지·Chrome·chrony·Bash·SSH/firewalld·Docker/Compose·업데이트 차단·화면 절전 방지를 기본으로 한다.
- NVIDIA는 항상 자동 감지하며 없으면 해당 없음이다. root Bash 테마와 Neovim/btop/tmux는 기본 꺼짐이다.
- 시간대 기본은 Asia/Seoul이다. DID 주소 미정이어도 환경 설치는 허용하되 화면 복구는 입력 대기다.
- 기능을 끄더라도 패키지 자동 삭제나 전체 설정 롤백은 하지 않는다. 자동 실행 off는 해당 등록만 해제한다.

## 공개 인터페이스

| 명령 | 동작 |
|---|---|
| `ala` | TUI |
| `ala config edit` | 구성 편집 |
| `ala config show` | 저장된 기대 구성 |
| `ala config import FILE` | JSON 검증 후 저장 |
| `ala setup`, `ala setup --plan` | 읽기 전용 실제 변경 계획 |
| `ala setup --apply` | 필요한 변경 후 검증 |
| `ala setup --apply --detach` | 독립 설치 시작 후 실행 ID 반환 |
| `ala status` | 현재 상태·작업 요약 |
| `ala check` | 기대 상태 검사 |
| `ala chrome` | Chrome 메뉴 |
| `ala chrome start/stop/restart` | 표시용 Chrome 제어 |
| `ala chrome status/logs/check` | Chrome 조회·검사 |
| `ala runs list`, `ala runs show RUN_ID` | 실행 기록 |
| `ala logs --run RUN_ID --follow` | 설치 로그 추적 |

show/status/check/plan/실행 기록에 --json을 제공한다. stdout JSON에는 일반 로그를 섞지 않는다.
CLI/TUI는 같은 서비스 계층과 결과를 사용한다. 비TTY 무인자 실행은 사용 오류 64이며 입력을 기다리지 않는다.
check/apply는 0 정상, 1 불일치·실패·차단·확인 불가, 2 적용·입력 대기, 잘못된 명령은 64다. 실패가 대기보다 우선한다.
계획은 변경이 필요해도 계산에 성공하면 정상 반환한다. 계산 자체의 차단·확인 불가는 구분한다.
TUI에는 대시보드/구성/설치·설정/검사/Chrome/실행 기록의 여섯 영역을 제공한다.
적용 전 계획 확인을 제공하고 화면 종료가 설치나 Chrome을 종료하지 않게 한다. 진행 중 RPM 취소 기능은 만들지 않는다.

## 공통 실행·검사 구조

- component별 inspect → plan → apply → verify 기준을 공유한다. 과거 완료 기록으로 실제 조사를 대체하지 않는다.
- 설치 전 재조사한다. 검사 실패 뒤에도 나머지 읽기 전용 검사는 계속한다.
- 결과에는 id, 상태, 기대값, 실제값, 다음 조치를 포함한다.
- 정상/변경 필요/대기/해당 없음/차단/확인 불가/실패를 구분한다. 명령 부재·권한 부족·네트워크 실패를 정상/미지원으로 단정하지 않는다.
- Bash·선택 도구·시간대·SSH 런타임/영구 방화벽 규칙·전체 dconf 값/lock/DB/logind까지 검사한다.
- plan/check/help는 설치·서비스 시작·설정 수정·백업 생성을 하지 않는다. 최종 DNF 의존성 트랜잭션의 사전 확정을 약속하지 않는다.
- root 소유 `/etc/ala/config.json`은 데이터로만 읽는다. source/eval/임의 명령 실행을 허용하지 않는다.
- `/opt/ala/releases/`와 current에 버전별 실행 코드·venv, `/usr/local/bin/ala`에 진입점을 설치한다.
- `/var/lib/ala/runs/`에 실행 ID/스냅샷/부팅 ID/unit/도구 버전/실제 release 경로/시각/단계 결과/로그를 보관한다.
- 새 백업은 `/var/lib/ala/backups/`에 둔다. Chrome managed 디렉터리 안에는 백업·임시 파일을 두지 않는다.
- 기존 dconf 이름과 NVIDIA 재부팅 기록을 인식하고 이름 변경만을 위한 재설정은 하지 않는다.
- 암호/토큰/브라우저 쿠키를 구성·일반 로그에 보관하지 않는다.

## 권한·독립 작업

- 일반 사용자 TUI에서 필요한 순간 sudo 인증을 받고 고정 root 실행기를 호출한다. Chrome은 일반 사용자로 실행한다.
- 시스템 systemd service가 설치를 수행한다. SSH 종료와 독립하며 실행 코드는 current가 아닌 실제 release에 고정한다.
- 설치·도구 갱신은 서버당 단일 변경 잠금을 공유한다.
- 전원 중단 후에는 interrupted로 판정하며 자동 설치 재개를 하지 않는다. 명시 재실행 시 실제 상태를 다시 확인한다.
- 조회는 중단 상태를 계산할 뿐 기록을 수정하지 않는다. 재부팅 대기를 완전 완료로 표시하지 않는다.
- Docker/GDM/현재 그래픽 세션/sshd 강제 재시작과 자동 재부팅을 하지 않는다.
- 정상 패키지와 동일 내용·권한·소유자 설정은 유지하고 mtime/백업 개수를 늘리지 않는다.
- Docker JSON과 사용자 셸의 다른 설정을 보존한다. Podman 충돌·고장 GPU·Secure Boot·외부 정책 충돌은 중단/진단하며 자동 제거·보안 우회를 하지 않는다.
- 자동 OS 업데이트 차단을 유지한다. 기존 Chrome 자동 업그레이드, SELinux 비활성화, SSH 인증 변경을 추가하지 않는다.

## GNOME·Chrome 복구

- GDM 관련 항목만 수정해 지정 계정의 자동 로그인을 구성하고 다른 설정을 보존한다. 해당 계정의 GNOME 첫 실행 안내 완료 상태를 준비한다.
- 새 `ala-chrome.service` 사용자 unit을 사용한다. GNOME autostart에서 실제 세션의 필요한 환경만 import하고 시작한다.
- graphical-session.target에 연결한다. 대상 계정의 그래픽 세션 하나만 지원하고 여러 세션을 임의 선택하지 않는다.
- DISPLAY=:0 추정이나 linger로 로그인을 대체하지 않는다.
- F11 전체화면과 번역/처음 실행/기본 브라우저/복원 안내 억제 설정을 유지한다. --kiosk/--no-sandbox/전체 Chrome 종료는 금지한다.
- 시작 전 URL 응답을 5초 제한으로 조회하고 10초 간격 재시도한다. TLS 검증을 유지하고 대기 이유를 노출한다.
- Restart=always, RestartSec=5, StartLimitIntervalSec=300, StartLimitBurst=5. 제한 도달 실패를 노출하고 명시 restart가 reset-failed 후 재시도한다.
- 페이지가 열린 후 지속 사이트 장애 감시/자동 새로고침은 제외한다.
- stop은 현재 실행만 중지하며 다음 그래픽 로그인/재부팅에는 자동 시작한다. 영구 중지는 구성의 자동 실행 off다.
- 기존 did-chrome.service는 적용 중 유지·전환 대기로 표시한다. 명시 restart나 다음 GNOME 로그인에서 기존 관리 unit 정지·종료 확인 후 신규 unit을 시작한다.
- 관리 밖 프로세스가 프로필을 점유하면 중단한다. 잠금 파일 삭제와 광범위한 pkill은 하지 않는다.

GPU 없음/정상/설치/재부팅/미지원/고장, 새 Chrome 프로필 격리/기존 보존/옵션/중복 방지/stop/restart/장애 제한,
부팅 URL 지연/키링 팝업 없음, TUI 키보드/크기/sudo/작업 중 종료, 설치·재설치·갱신·원본 삭제를 검사한다.

Textual headless Pilot으로 화면 동작을 검사한다.
실기기 CPU→GPU에서 첫 적용→재실행→SSH 재접속→재부팅→복구를 확인하고 실제 GPU 컨테이너도 실행한다.
실행 인자 검사만으로 실제 창·팝업·내용 수용을 완료했다고 주장하지 않는다. 대상·유지보수 시간·화면 확인 경로가 없으면 미검증으로 남긴다.

AGENTS.md, 이 문서, ala-v1-progress.md를 시작/재개 시 읽고 git 상태·diff·기록 커밋과 대조한다.
