# ala 공개판 계획

## ALA-32 이후 — 화면 관리·자동 갱신

최신 승인 구현은 [화면 관리·자동 업데이트·프론트 갱신 계획](ala-display-update-plan.md)을 따른다.
세 탭·대상별 Chrome·GNOME 배치·정식 CLI 자동 갱신·야간 관리 코드 전환·프론트
배포 기반 갱신을 추가한다. 이전 두 탭/수동 갱신 범위를 확장한다.

## 제공 범위

Rocky Linux 10 x86_64 + GNOME/GDM 환경에서 기존 일반 사용자를 대상으로 설치·설정·검사·Chrome 표시를 관리한다.
Python 3.12, argparse, Textual과 내부 Bash 모듈을 사용한다.
OS 설치·파티션·애플리케이션 배포·DB 운영·DID 패널 제어는 제외한다.

## 유지할 계약

- 현재 상태 조사 → 변경 계획 → 적용 → 재검사. 이미 정상인 패키지와 동일 설정은 유지한다.
- plan/check/status는 설치·서비스 변경·설정·백업 생성을 하지 않는다.
- root 고정 실행기와 systemd 작업은 SSH 종료와 독립한다. 설치·갱신은 같은 잠금을 사용한다.
- 기존 구성·Chrome 프로필·Docker 설정을 보존한다. 실행 중 서비스 강제 재시작이나 자동 재부팅은 하지 않는다.
- 새 표시 프로필, 일반 사용자 Chrome, GNOME 자동 로그인·잠금/절전 방지, F11 전체화면을 사용한다.
- 표시용 Chrome만 --password-store=basic을 사용한다. 이 프로필에 인증정보를 저장하지 않는다.
- setup은 전체 OS 업데이트를 하지 않는다. prepare는 별도 최초 공식 OS 준비와 명시적 재부팅 검증이다.
- NVIDIA 및 공식 드라이버 누락을 조사한다. 미지원·초기화 실패를 자동 패키지 삭제/보안 우회로 해결하지 않는다.
- 네트워크 진단은 연결을 변경하지 않는다. 외부 probe는 명시 옵션이며 호스트 통신과 Wi-Fi 통신을 구분한다.
- 실제 화면 관찰을 프로세스 인자·모의 테스트로 대체하지 않는다.

## 공개 배포 준비

1. 공개 코드·문서·테스트를 유지하고, 원래 개발 이력은 민감한 내용을 정리해 작성자·날짜·병합 관계를 보존한 채 연결한다.
2. 인증 없는 HTTPS 다운로드·설치·수동 갱신 절차를 문서화한다.
3. 기존 버전은 덮어쓰지 않고 새 후보를 빌드·검증·게시한다.
4. CPU/GPU 실기기 수용 후 정식 버전을 판단한다.

## 자동 갱신 범위와 남은 수용

ALA-32~38에서 주기적 타이머, 서명 검증, CLI와 화면별 관리 버전 분리,
야간 순차 적용과 복원을 구현했다. 자동 운영은 기본 꺼짐이며, 실제 보호 환경·태그
규칙과 서명 릴리스 검증, GNOME·모니터·재부팅 수용을 마친 뒤 활성화한다.
중앙 장비 관리와 장비 상태 보고는 이번 범위에 포함하지 않는다.

## 검증

읽기 전용·멱등성·권한 분리·설치 잠금·실행 기록·GPU/네트워크 진단·TUI·배포 설치 회귀를 유지한다.
실제 장비에서 첫 적용 → 재실행 → SSH 재접속 → 재부팅 → 화면·GPU 수용을 별도로 수행한다.

## ALA-13 — 목적 중심 첫 화면과 순서형 설정

- 첫 화면은 처음 설정/현재 설정 보완, 서버 상태 확인, 화면 관리, 고급 설정 네 진입점으로 줄인다.
- 순서형 설정: 기존 계정 확인 → 바탕화면/DID 선택 → 필요한 변경 요약 → 명시적 설정 시작 → 진행/다음 행동.
- sudo는 시작 동선에서 처리하고 암호는 sudo가 직접 받는다. 기존 고급 구성·OS 준비·실행 기록은 고급 설정 아래 유지한다.
- 저장된 선택 옵션을 보존하며 계획 판정·구성 변경 감지·단일 작업·백그라운드 실행 계약을 재사용한다. 사용자에게 plan/apply 개념을 요구하지 않는다.
- 80×24 키보드 흐름, 취소/실패/중복/계획 불일치/재접속을 headless 테스트한다. 기존 CLI/설치 엔진 회귀도 유지한다. RC4를 덮어쓰지 않고 새 RC5로 준비한다.

## ALA-14 — 새 버전 안내·명시적 자체 갱신

- 시작 화면에서 비동기 읽기 전용 업데이트 조회. 실패해도 환경 관리를 막지 않는다.
- ala update --check [--json], ala update [--prerelease]. 기본은 정식판, 시험판은 명시 선택. 버전 숫자 비교로 다운그레이드 방지.
- 공개 GitHub API와 고정 저장소 자산만 사용하며 인증정보를 요구/저장하지 않는다. HTTPS와 SHA-256·manifest 검증. 이는 서명 검증과 다르다.
- root 고정 실행기가 systemd 작업으로 갱신하여 SSH 종료와 분리한다. 기존 installer의 잠금·원자적 current 전환·구성 보존을 재사용한다.
- RC5는 불변. 기능 포함 버전으로 최초 수동 갱신 필요. 자동 적용·정기 타이머는 범위 밖.

## ALA-15 — 가독성·차단 원인 우선 화면

- 차단 상태와 재부팅 등 적용 대기를 분리한다. 차단 패키지·실제 상태·다음 조치를 숨기지 않는다.
- 차분한 색상, 상태 카드, 명확한 포커스, 접는 상세 내역으로 정보 밀도를 줄인다. 80×24에서도 키보드로 접근 가능해야 한다.
- Podman 차단은 Docker 공식 RHEL 설치 안내에 근거해 유지하며 자동 삭제하지 않는다. 기존 일반 사용자/root 컨테이너·볼륨 점검 절차를 안내한다.
- 모의 Podman 화면·정상 화면을 렌더링하고 키보드·회귀 테스트 후 RC7 후보로 제공한다.

## ALA-16 — 단계별 집중형 화면

- 사용자 선택: 가운데 작업 메뉴, 한 화면에 한 작업. 기존 왼쪽 고정 메뉴를 제거한다.
- 홈은 작업 이름+설명 목록, 설정은 계정/화면/확인의 진행 표시와 고정된 이전/다음 버튼을 사용한다.
- Esc/상단 홈으로 언제든 작업 목록에 돌아가며, 상세 화면으로 전환하면 해당 내용에 포커스를 둔다.
- 80×24/120×36, 크기 변경, 차단/정상/작업 진행, 키보드와 무색 터미널을 검증한다.
- 설치 엔진·명시적 적용·단일 변경 작업·구성 보존 계약 유지. RC8 후보로 준비한다.

## ALA-17 — 실행 시 관리자 인증

- 사용자 결정: 설치·설정에 필요한 관리자 권한으로 실행되도록 한다. 대화형 ala 시작에서 sudo 인증 후 전체 관리 화면을 root로 실행한다.
- 검증된 설치 릴리스의 고정 Python/entry를 재실행하며 현재 버전에 고정한다. 소스 폴더를 자동 승격하지 않는다.
- help/version/update --check는 인증 없이 유지한다. 비대화형 CLI는 기존 sudo -n 관리자 RPC를 유지해 암호 입력으로 멈추지 않는다.
- sudo ala도 지원한다. 화면 계정은 저장된 일반 사용자 또는 원래 sudo 사용자를 사용하며 Chrome/user service는 일반 사용자로 유지한다.
- 디자인 추가 변경은 사용자의 구체적 불편·참고 방향을 확인한 뒤 결정한다. 이 단계에서는 임의의 새 테마를 추가하지 않는다.

## ALA-18 — 간편 설정·상태 확인만 기본 제공

- 최신 사용자 결정: 원래 setup-base.sh처럼 간편 설정 한 번과 의도한 상태 검사면 충분하다. 기본 전체화면/여러 단계 TUI를 일반 터미널의 짧은 진입 화면으로 대체한다.
- 기본 ala: Enter 간편 설정, s 상태 확인, q 종료. 관리자 인증 후 저장된 설정을 재사용하며 처음이면 sudo 실행자의 일반 계정과 기본값을 사용한다.
- 간편 설정은 기존 submit/설치 엔진으로 한 번에 적용한다. 작업별 실제 상태를 재검사하고 위험한 패키지 삭제 등은 기존 엔진에서 차단한다.
- 최초 적용 때만 검증한 기본 구성을 공통 잠금 안에서 저장한다. 조회는 저장하지 않으며 기존 구성은 덮어쓰지 않는다.
- 상태는 기능별 정상/변경 필요/적용 대기/확인 불가를 요약하고 문제의 실제값·다음 조치를 보여준다. 전체 JSON은 유지한다.
- 기존 TUI는 ala tui 및 명시적 상세 명령으로만 접근한다. 재부팅/전체 OS 준비는 기존 명시적 작업을 유지한다.
- ALA-16의 기본 집중형 전체화면 결정을 이 결정으로 대체한다. RC9 후보에 관리자 진입과 간편 흐름을 함께 반영한다.

## ALA-19 — TUI 유지, 두 화면으로 단순화

- 사용자 정정: TUI는 필요하고 기존 네 메뉴가 과했다. ALA-18의 기본 텍스트 화면 결정을 기본 TUI로 되돌린다.
- ala / ala tui는 간편 설정과 상태 확인 두 화면만 제공한다. 다단계 wizard 없이 저장된 구성 또는 기본 계정으로 간편 설정 버튼 한 번에 submit한다.
- 초기 조회와 상태 화면은 읽기 전용이다. 기존 root 진입·공통 잠금·첫 구성 저장·작업 지속·단계별 엔진 차단은 유지한다.
- 진행 중 작업 재접속/중복 실행 차단/기능별 상태·원인·다음 조치/키보드·80×24를 검증한다. 상세 JSON과 명시적 기존 명령은 유지하고 텍스트 콘솔은 ala console로 선택한다.
- Podman을 자동 삭제하지 않는다. 정확한 조회 명령과 직접 제거 전 검토 절차를 안내하며 폐기된 '이전→변경 확인' 문구를 기본 흐름에서 제거한다.
- 담당 분리: 두 화면 TUI+테스트, Podman 판단 읽기 전용 검토를 에이전트에 위임. 주담당은 CLI 통합·문서·공개 검사·CI·RC10 후보.

## ALA-20 — 설치 항목별 현재 진행 상태

- 간편 설정에도 기능별 표를 제공한다. 이벤트 이력 누적 대신 항목별 마지막 상태를 한 행에서 갱신한다.
- 완료/정상 유지 초록, 진행 중 청록, 대기 노랑 또는 회색, 차단/실패 빨강으로 표시하며 한국어 라벨·기호를 함께 쓴다. kept 원문을 표시하지 않는다.
- 아직 실행하지 않은 단계는 대기/미실행으로 표시한다. 스크립트 완료 이벤트보다 최종 검사 불일치·재부팅 대기를 우선하며 진단 실패 원인을 숨기지 않는다.
- 상태 표는 선택·스크롤 위치를 유지하고 실행 중 단계는 사용자가 상세를 탐색하지 않을 때 따라간다. 선택한 항목의 원인·다음 조치를 하단에 표시한다.
- 설치 엔진·작업 기록 포맷은 바꾸지 않는다. 순수 상태 투영 모델과 UI 통합을 분담하고 모의 진행/재접속/최종 결과를 검증한다. RC11 후보로 준비한다.

## ALA-21 — 큰 기능 안의 세부 설정 표시

- 사용자가 큰 기능 내부의 구성 항목과 어떤 설정을 처리하는지 보기를 요청했다. 기본 두 탭은 유지한다.
- 큰 기능 행에 실제 진행 중인 세부 작업을 표시하고 Enter로 해당 기능의 세부 항목을 펼쳐 상태를 확인한다. 상태/색상은 기존 계약을 재사용한다.
- 정적 카탈로그는 실제 스크립트·검사 ID와 매핑한다. 실행 중이라는 판정은 추측하지 않고 구조화된 substep 신호가 있을 때만 표시한다.
- Shell은 opt-in 구조화 마커를 기존 명령 앞뒤에서 보고한다. root worker는 허용 ID/state만 additive substeps 기록에 저장한다. 일반 로그의 문장을 상태로 추측 파싱하지 않는다.
- 원래 스크립트의 명령·실패·종료·보안 정책을 유지한다. 기존 실행 기록에 세부 신호가 없으면 확인 전으로 표시하고 재접속/최종 검증/미실행을 구분한다.
- 카탈로그/순수 모델과 Shell 마커를 분담하고 주담당은 스트리밍·worker·TUI·통합·RC12 후보를 관리한다.

## ALA-22 — TUI 여백과 반응형 배치

- RC12 사용 화면에서 버튼·설정 요약·진행 표가 붙고 긴 항목이 잘리는 문제를 개선한다. 기본 두 탭과 기존 실행 흐름을 유지한다.
- 계정/표시 정보와 실행 버튼을 툴바로 묶고, 작업 요약·진행 표·선택 상세 사이 간격과 제목을 분리한다. 넓은 화면에서는 내용 최대 폭과 열 폭을 늘린다.
- 80×24는 압축 배치를 사용하며 더 높은 화면은 상하 여백과 행 간격을 늘린다. 상세·버튼·하단 키 안내는 화면 안에 유지하고 표는 스크롤로 탐색한다.
- 상태 의미/설치 엔진/실제 장비 설정은 바꾸지 않는다. 레이아웃 검증을 분담하고 실제 Textual 합성 화면을 여러 크기로 렌더링한다.
- 새 RC13 후보로 제공하며 RC12 파일은 변경하지 않는다.

## ALA-23 — 상태 조회 지연과 화면 구분

- Rust 재작성에 앞서 실제 병목인 외부 명령의 직렬 대기·동일 조회 반복을 줄인다. 실제 서버 성능은 별도 측정하며 모의 수치를 실제 개선율로 주장하지 않는다.
- 읽기 전용 status/inspect/plan의 독립 검사는 제한된 병렬 실행과 조회 한 번 안의 동일 명령 공유를 사용한다. 설치 전후 재검사와 변경 실행은 캐시를 공유하지 않는다. 실패·권한·시간 초과 판정과 결과 순서는 유지한다.
- 상태 JSON에 검사별 소요 시간과 전체 시간을 추가해 장비에서 병목을 확인할 수 있게 한다. 설정·실행 중 작업 정보는 전체 검사 완료를 기다리지 않고 먼저 표시한다.
- 두 탭은 유지하고 설정 대상/현재 작업/검사 결과/선택 상세를 표면·제목·강조로 구분한다. 부모와 자식 계층을 강화하고 최초 조회 중·갱신 중을 표시한다.
- 세부 기록 없음과 실제 조회 실패를 표시 이유로 구분하며 원래 CheckResult 판정과 종료 코드는 유지한다. 정상 집계는 합쳐 조치·적용 대기를 구분하기 쉽게 한다.
- 성능/읽기 전용 검증과 TUI/이유 표시 검증을 분담한다. RC14 후보로 준비하며 기존 RC13 파일은 유지한다.

## ALA-24 — Chrome 자동 등록·현재 세션 시작 보완

- 사용자가 간편 설정 완료 후에도 Chrome 자동 시작 등록이 설정 필요, 실행 확인이 적용 대기라고 보고했다. 실제 장비 SSH 조회는 연결 거절로 확인하지 못했으며 진단 문구를 기다린다. 모의 코드 재현과 실제 원인은 구분한다.
- unit/desktop 파일은 버전별 RELEASE 경로 대신 설치기의 고정 `/usr/local/bin/ala` 진입점을 사용한다. 첫 명시적 setup에서 기존 ala 관리 파일만 백업·이전한다. 이후 도구 버전만 바뀌어도 등록 불일치가 생기지 않게 한다.
- setup은 등록 후 URL·단일 활성 그래픽 세션·user manager 환경이 준비된 경우 중지된 새 ala Chrome의 시작까지 처리한다. 정상 실행·기존 did-chrome·외부 프로필 사용·실패 제한 상태를 강제 재시작하지 않는다. root Chrome/DISPLAY 추정/GDM 강제 재시작/자동 재부팅은 금지한다.
- 화면 정책·Chrome 등록은 기본 환경/업데이트 안전 검사/장치/셸/SSH 다음, Docker/GPU보다 먼저 직렬 적용한다. Docker/GPU 차단 때문에 등록을 놓치지 않게 하며 원래 오류와 종료 코드는 보존한다. 일반 DAG·설치 병렬화는 이번 범위가 아니다.
- 적용 대기는 원인·다음 행동을 우선 표시한다. 재로그인/사이트 응답 대기 등 외부 조건과 자동 등록 미적용을 구분한다. 조회는 설정하지 않는다.
- display/engine/표시 개선을 분담해 회귀·멱등성·일반 사용자·구버전 등록 이전을 검증한다. RC15 후보로 준비하며 RC14 파일은 변경하지 않는다.

## ALA-25 — TUI 화면 설정·다중 표시 대상 요구 확인

- 사용자는 별도 Shell 명령 대신 ala 화면 안에서 표시 대상과 URL을 설정하고 적용·시작·중지·재시작까지 관리하려 한다. RC15는 단일 URL/Chrome의 자동 등록·시작 보완이며, 모니터별 배치 기능을 구현한 버전이 아니다.
- 기본 두 탭은 유지하고 화면 설정 진입점에서 대상·URL·자동 실행을 편집하는 방향으로 검토한다. 화면 제어는 기존 일반 사용자 RPC와 변경 잠금을 재사용하며, 저장·현재 적용·재부팅 후 복구를 구분한다.
- 패널 수를 OS 출력 수로 간주하지 않는다. 먼저 실제 사용자 그래픽 세션에서 GNOME 물리/논리 출력, 활성 모드·좌표·스케일을 읽기 전용으로 조사한다. 조회 실패와 출력 없음, 동일 논리 화면 복제를 구분한다.
- 외부 장비의 단일 신호 복제는 PC에서 패널별 다른 콘텐츠로 배치할 수 있다고 표시하지 않는다. 합성 화면 분할은 영역/콘텐츠 구성, 독립 논리 출력은 출력별 창 매핑으로 분리하며, 장비 자체의 라우팅·패널 배치는 계속 별도 제어 범위다.
- 배치 방법은 실제 GNOME/Chrome 환경에서 검증한 뒤 결정한다. Chrome 위치 인자만으로 정확한 전체화면 배치를 보장하지 않으며, 한 논리 화면의 여러 영역을 각각 독립 모니터 전체화면으로 취급하지 않는다.
- 구현 순서는 출력 조사와 지원 판정 → 검증 가능한 배치 방식 → 기존 단일 구성 호환·대상별 프로필/서비스·상태 → TUI 편집/제어 → 재로그인·재부팅 수용이다. 목표 출력 부재·중복 매핑·잘못된 위치를 성공으로 표시하지 않는다.
- 현재는 연결/입력 구조 확인과 범위 정리 단계이며 기능 구현·다중 화면 실기기 검증·후보 게시를 완료로 기록하지 않는다.

## ALA-26 — 업데이트 완료 확인·실패 판정

- ala update는 백그라운드 worker 시작과 최종 설치 완료를 구분한다. 기본 CLI는 상태를 추적하고 --detach로 표시만 먼저 종료할 수 있게 한다. Ctrl+C·TUI 종료·SSH 종료는 worker를 중단하지 않는다.
- root 소유 업데이트 실행 기록에 단계·대상 버전·변경 전후 설치 버전·부팅 ID·unit·완료/실패를 원자 저장한다. update --status [--json]은 읽기 전용 재조회이며 진행 중·중단·확인 불가를 성공으로 판정하지 않는다.
- 현재 실행 코드 버전과 /opt/ala/current의 실제 설치 버전을 구분한다. 설치기 종료 후 대상 버전과 entry 실행을 재검사하고 일치해야 완료다. 실패 후에도 실제 포인터를 확인하며 모든 실패를 기존 버전 유지로 단정하지 않는다.
- GitHub/API·다운로드·TLS·해시·manifest·설치 실패를 구분해 표시한다. 조회 실패를 업데이트 없음으로 취급하지 않으며 읽기 조회는 파일·서비스를 변경하지 않는다.
- 두 탭은 유지하고 업데이트 관리창에서 조회·명시적 적용·진행·완료·실패를 확인한다. 새 버전 설치 뒤 현재 TUI가 구버전이면 다시 실행해야 함을 표시한다.
- 업데이트 상태 계층과 TUI를 분담하고 root는 CLI/RPC·통합·배포를 맡는다. 기존 변경 잠금·고정 worker·검증된 배포물만 설치하는 계약을 유지한다.

## ALA-27 — 표시 사이트 지속 감시·복구

- 시작 전 URL 검사와 실행 중 사이트 감시를 구분한다. 정상 화면을 일정 주기로 무조건 새로고침하는 방식 대신 장애 확인·재시도·복구 후 복귀를 설계한다.
- HTTP 오류·DNS·TLS·timeout·브라우저 종료와 실제 화면 내용·앱 상태를 구분한다. 외부 URL의 HTTP 200만으로 앱·페이지 정상이나 장애 화면 부재를 보장하지 않는다. 별도 앱 heartbeat 없는 내부 데이터 장애는 확인 범위 밖이다.
- 사용자 선택: 사이트 장애 중에는 로컬 ‘연결 복구 중’ 안내를 표시하고 복구 확인 후 자동 복귀한다. 정상 시작은 첫 HTTP 확인 후 관리 주 문서를 관측하고, 장애 후에는 연속 정상 2회를 확인한다. HTTP 확인은 30초 간격·5초 제한, 연속 실패 3회이며 주 문서 탐색 오류는 별도로 즉시 복구한다.
- 표시용 프로필·일반 사용자 supervisor·CDP pipe만 관리하고 다른 Chrome·프로필을 제어하지 않는다. 네트워크 디버깅 포트는 열지 않는다. 부팅/프로세스 시작 식별자/기록 신선도와 실제 Chrome 인자를 대조하고 구버전 단독 Chrome은 강제 재시작 없이 감시 전환 대기로 남긴다.
- 감시 결과와 마지막 확인·재시도·다음 행동을 CLI/TUI에서 볼 수 있게 한다. 시작 요청·프로세스 존재·HTTP 응답·현재 탭 검사·실제 모니터 수용을 서로 대체하지 않는다.
- ALA-25의 다중 출력·외부 DID 장비 제어와 별도로 구현한다. 실행 이후 감시 구현·모의 검사·실기기 수용을 구분해 기록하며 RC16 후보로 준비한다. 기존 RC15는 변경하지 않는다.

## ALA-28 — 설정과 현재 Chrome 관리 분리·프로세스 확인 보완

- 최신 사용자 결정으로 ALA-24의 setup 현재 세션 자동 시작을 대체한다. 간편 설정은 GDM 자동 로그인·Chrome 부팅 자동 실행·프로필·정책 등록만 적용하고 현재 Chrome을 시작·중지·재시작하지 않는다. 실제 로그인 뒤 autostart→사용자 service와 비정상 종료 복구는 유지한다.
- 설정 계획/적용 완료는 구성 준비를 검사한다. Chrome이 현재 중지됐거나 그래픽 세션이 아직 없다는 이유로 설정 완료를 실패로 바꾸지 않는다. URL 등 필요한 입력의 대기는 유지한다. 전체 status/check와 화면 관리는 실제 세션·프로세스·사이트 감시를 별도로 검사한다.
- status의 configuration_report는 동일 검사 패스의 정적 결과이며 이중 전체 조사를 하지 않는다. 설정 plan/apply Report에는 scope=configuration을 추가해 실행 기록과 TUI가 구성 결과/전체 관측을 구분한다. scope가 없는 과거 결과는 원래 기록을 보존한다.
- 기본 두 탭은 유지하고 c/화면 관리 버튼으로 시작·중지·재시작·현재 상태·로그를 관리한다. 설정 준비/부팅 자동 실행과 현재 실행/사이트 상태를 나누고, 명령 접수만으로 실제 화면 정상이라고 표시하지 않는다. 다중 출력/외부 장비 배치는 ALA-25 확인 범위로 유지한다.
- cgroup 문자열 완전 일치만으로 Chrome 자식 관계를 판정하지 않는다. 동일 사용자·부팅·양쪽 프로세스 시작 ID·직접 PPid·실제 표시 프로필/인자 같은 독립 증거로 검증하고, cgroup이 달라도 정상 자식이면 허용한다. 무관 PID·재사용·잘못된 인자·조회 불가는 정상으로 처리하지 않는다. 프로세스 확인 실패 뒤 health 정상 행을 남기지 않는다.
- 부팅 설정 준비와 실제 재부팅/모니터 표시 수용을 구분한다. GDM이나 현재 화면을 강제로 재시작하거나 PC를 자동 재부팅하지 않는다. 화면 중지는 현재 실행에만 적용하고 다음 로그인 자동 시작을 끄려면 구성을 변경한다.
- display/프로세스 검증과 TUI를 분담하고 root는 Engine 계획/적용·RPC 통합·문서·후속 PR과 RC17 후보를 맡는다. 이전 RC16 배포 파일은 변경하지 않는다.

## ALA-29 — Linux Chromium 프로세스 제목 형식 검사 보완

- 사용자에게 값 없는 proc 형태 진단을 받아 단일 인자/제목 내부 switch 존재/Chrome 실행 파일 패턴을 확인했다. Chromium Linux의 SetProcessTitleFromCommandLine이 argv를 공백 결합한 제목으로 재작성하는 공식 구현 및 현재 검사 합성 재현과 일치한다. 실제 설정 누락과 표시 형식 오인을 구분한다.
- NUL argv와 지원 가능한 Linux 제목 형식을 공통 관측 계층에서 구분한다. 평탄 제목을 무조건 shlex/공백 복원해 일반 argv로 신뢰하지 않고 실행 파일·공백/제어 문자·예상 인자·옵션 경계 등 지원 조건을 좁힌다. 모호한 형식은 확인 불가 하나로 안내하며 정상으로 우회하지 않는다.
- 기존 UID/직접 PPid/동일 부팅/양쪽 시작 식별자/표시 프로필·실제 옵션 검증을 유지한다. 중복·잘못된 옵션·금지 플래그는 계속 차단하고 관리 밖 프로필 감지에도 같은 형식 차이를 반영한다. 공개 진단에는 argv·URL·계정 경로를 넣지 않는다.
- Linux 프로세스 제목을 반영한 회귀와 가능한 실제 Linux headless Chrome 검증을 추가한다. Mac에서 같은 함수가 no-op라는 차이를 기록하고 Mac 스모크를 Linux 검사 증거로 대체하지 않는다.
- parser/display 통합과 독립 검사/테스트를 분담하고 root는 Linux 통합 검증·문서·PR/RC18 후보를 맡는다. 설정/실행 관리 분리와 기존 프로필·현재 Chrome·RC17 배포 파일은 유지한다.

## ALA-30 — 정상 화면 재탐색 진단과 복구 안내 누락 보완

- 사용자가 외부 테스트 사이트의 안내 없는 주기적 재로딩을 보고했다. 두 관측의 감독/브라우저 PID와 healthy/HTTP 정상 상태가 동일하여 프로세스 재기동은 관측되지 않았다. 같은 탭 재탐색과 페이지 자체 동작은 아직 구분하지 못하며 실제 원인을 확정하지 않는다.
- PR #7 병합 573a212 기준 새 codex/chrome-refresh-observation에서 진행한다. 정상 HTTP probe는 탐색하지 않는 계약을 유지하고 사이트 JavaScript/meta refresh를 임의 차단하거나 Chrome/GDM을 강제 재시작하지 않는다.
- 초기 표시 주소 탐색의 errorText/isDownload가 탐색 시작 표시보다 앞서 처리되어 실제 복구 안내를 요청하지 않고 재시도할 수 있는 재현 경계를 수정한다. 실제 안내로 전환하며 반복 복구 안내 요청은 억제하고 원래 HTTP 복구 확인·TLS·대기 간격을 유지한다.
- 감시 JSON에 supervisor_version과 navigation을 추가한다. navigation은 display_requests/recovery_requests/browser_navigations 카운터, last_command(kind/at), last_browser_navigation(initiator/at), last_error(kind/at)를 저장한다. 명령 접수/실제 문서 관측을 구분하고 브라우저 관측을 사이트 원인 확정으로 표현하지 않는다. URL·제목·스크립트·스택·쿠키는 저장하지 않는다. initiator/error는 고정 범주만 기록한다.
- 기존 UID/부모/부팅/시작 식별자와 상태 검사·구성 호환을 유지한다. 과거 실행에 진단 기록이 없으면 0회로 추정하지 않고 전환 대기를 표시한다. TUI 화면 관리 상세에서 카운터를 읽기 전용으로 확인한다.
- 분담은 display_health 구현/독립 회귀/TUI 표시·검증으로 나눈다. root는 통합·계획·배포·새 PR·RC19를 담당한다. 정상 probe 추가 탐색0, 명령 실패의 안내 요청, 페이지 주도 동일주소 재탐색 구분, 불명/잘못된 진단의 정상 오인 방지를 검증한다. 실제 장비 원인과 자동/격리 실측 결과를 구분한다.

## ALA-31 — 로그인 자동 시작 연결·준비 대기·부팅 로그 보완

- 부팅 후 화면 계정/등록/현재 그래픽 환경은 준비돼 있지만 Chrome이 유지되지 않는 보고를 조사한다. GNOME의 로그인 진입점 호출은 확인했으나 해당 진입점이 실패 이유를 버려 실제 중단 지점을 확정하지 못했다. systemd의 현재 실행 시각0은 GC 후 재로딩에서도 나타나므로 부팅 전체의 미실행 증명으로 쓰지 않는다.
- 기존 codex/chrome-refresh-observation/열린 PR #8에 통합한다. RC19은 변경하지 않고 새 RC20 후보를 만든다. 실제 장비의 구체 원인과 재현 가능한 코드 취약점을 구분한다.
- 로그인 진입점은 설정/일반 사용자 검증 후 서비스 시작 요청을 한 번 연결한다. 준비가 덜 된 활성 세션/화면 때문에 서비스 요청 전에 조용히 종료하지 않도록 실제 그래픽 준비 대기는 관리되는 Chrome 사용자 서비스 안에서 제한된 시간에 수행한다. 사용자의 stop/로그아웃은 그 대기 프로세스도 종료하며 외부 지연 작업이 나중에 다시 켜지 않게 한다.
- 실제 GNOME 환경만 화이트리스트로 가져오고 진입점에 화면 변수가 없으면 GNOME이 사용자 manager에 전달한 환경을 서비스에서 검증한다. DISPLAY 추정·root Chrome·linger·다중 세션 임의 선택은 금지한다. 현재 실행은 유지하고 같은 로그인 진입점 중복 호출로 Chrome을 재시작하지 않는다. 기존 관리 legacy 서비스는 다음 로그인 전환 계약을 유지한다.
- fresh/inactive 시작에 불필요한 reset-failed를 선행하지 않는다. 명시적 restart에서 필요한 실패/시작 제한 초기화는 유지한다. 로그인 연결 실패/명령 반환 코드는 값 없는 고정 phase/outcome을 ala-autostart 접두사로 기록하고 시작 요청을 실제 화면 성공으로 표시하지 않는다.
- 세션 종료·교체 취소는 전용 private 종료 코드78을 사용하고 unit의 SuccessExitStatus=78 / RestartPreventExitStatus=78로 정상 취소·재시작 억제를 명시한다. 일반 브라우저 장애의 Restart=always는 유지한다. 등록 문자열 무변경 선호보다 실제 취소 보장을 우선하므로 이번 버전은 기존 설치에서도 setup1회 후 재부팅 수용이 필요하다.
- Chrome의 첫 제어 연결/관리 탭 생성도 짧은 횟수 대신 제한된 시작 시간 안에서 기다린다. 응답 대기 timeout만 구분해 재시도하며 부분 전송·프로토콜 오류·다중 탭·자식 종료를 무시하지 않는다. 기존 restart 제한은 유지한다.
- 화면 관리 로그는 사용자 저널 파일이 없는 환경에서도 root RPC가 동일 UID·고정 Chrome unit/부팅 진입점의 시스템 저널만 읽을 수 있게 보완한다. 사용자·URL·쿠키·인증정보를 공개 기록에 저장하지 않고 기존 로그 표시 보호를 유지한다.
- 담당은 display 로그인/준비 대기, CDP cold start, UID 제한 저널 fallback으로 나눈다. root는 계약/통합·문서·CI/RC20을 맡는다. 모의·실제 Linux headless·실제 Rocky GNOME 재부팅/모니터 수용을 구분한다. 배포 후 실제 부팅에서 자동 시작과 화면을 다시 관찰하기 전에는 실기기 완료로 표시하지 않는다.
