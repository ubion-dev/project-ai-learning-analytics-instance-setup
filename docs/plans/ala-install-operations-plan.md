# 최초 설치와 운영 연결 설계 초안

이 문서는 설계 인터뷰에서 합의한 다음 개발 범위를 정리한다. 구현 완료·실제 장비 수용·배포 승인을 뜻하지 않는다. 기존 기능과 보호 계약은 유지한다. 기존 계획에서 제외했던 애플리케이션 배포 중 지정된 분석 서버의 최초 설치 연결을 추가 대상으로 삼으며, DB 운영이나 임의 애플리케이션 배포 전반으로 확대하지 않는다.

## 목적과 역할

합의한 범위의 구체적인 개발 순서와 완료 기준은 [첫 구현 계획](ala-first-implementation-plan.md)에 정리한다. 해당 문서도 설계 검토용이며 코드 구현 완료나 실제 장비 적용 승인을 뜻하지 않는다.

- OS 설치와 SSH 준비 이후 운영자가 ala로 환경 준비와 지정 버전 분석 서버의 최초 설치·서비스 등록·준비 상태 확인을 이어서 수행한다.
- 기존 OS 환경·Docker/GPU·Chrome·화면 배치·점검·업데이트·복구 기능을 유지한다.
- 분석 서버의 구현과 PC·서비스 운영 및 카메라 제어 API는 별도 분석 서버 저장소에서 담당한다. 같은 호스트 변경을 두 저장소에서 각각 구현하지 않는다.
- 교내 어드민 백엔드 담당자에게 [연동 가이드](../device-management-integration.md)를 인계한다. 실제 API·인증·네트워크 규약은 담당자와 후속 확정한다.
- 회사 공통 관리 서비스는 향후 조직 간 버전·정책·결과 관리를 담당하며, 회사 서비스와 연결되지 않아도 교내 운영을 유지한다. 최소 구현 범위와 착수 시점은 미결정이다.

## 최초 설치의 끝점

장비 역할은 `표시 담당`(관리 API·Chrome)과 `분석·표시 담당`(관리 API·Chrome·STT·CCTV 분석)으로 나눈다. 관리 기능은 분석 서비스의 중지·교체 중에도 사용할 실행 경로를 둔다. 역할을 하드웨어 등급과 같은 의미로 고정하지 않는다.

Mac에서 장비별 역할·화면 주소·분석 설정을 준비하고 대상 PC에 전달해 ala로 검토·적용하는 흐름을 채택한다. 공통 OS 이미지와 장비별 설정에 같은 설정 절차를 재사용하고, 실제 인증정보는 이미지·공통 템플릿과 분리해 전달한다. 장비 목록·설정 전달의 구체 스키마와 구현 방식은 후속 확정한다.

1. 현재 장비·기존 구성·필요 조건을 읽기 전용으로 확인한다.
2. 적용 대상과 필요한 변경을 확인하고 명시적으로 작업을 시작한다.
3. 기존 환경 준비 기능으로 필요한 항목만 적용한다.
4. 지정한 분석 서버 배포물을 검증하고 설치·등록한다. 정확한 배포 위치·인증·호환 버전 계약은 미결정이다.
5. 등록·프로세스 실행·서비스 준비 상태를 구분해 재검사한다. 분석 배포물이 준비되지 않은 경우 환경 준비 완료와 분석 서버 준비 대기를 구분한다.
6. 미완료 원인과 후속 작업을 표시하고 다시 접속해 같은 작업의 결과를 조회할 수 있게 한다.

분석 서버가 준비됐다는 판정과 마이크·카메라 입력으로 실제 분석 결과가 표시된다는 판정은 구분한다. 실제 장비·GPU·화면·재부팅 수용은 별도 기록으로 검증한다.

## 배포와 데이터

- 분석 서버는 버전이 고정된 컨테이너 이미지와 Compose 구성으로 제공한다. 조회 시점의 최신 버전과 실제 적용할 버전을 구분한다.
- 장비별 설정·모델 파일·분석 결과·저장 데이터는 서비스 교체와 분리해 보존한다. 데이터 삭제는 별도 명시 작업이다.
- 데이터 형식이 변경되는 배포는 호환·이전·복구 조건을 요구한다. 프로그램의 이전 버전 선택만으로 데이터 복구가 완료됐다고 판정하지 않는다.
- Chrome은 기존 일반 사용자 실행·프로필 보존 계약을 유지한다. 분석 서비스의 컨테이너화 때문에 Chrome을 root 컨테이너에서 실행하지 않는다.

## 운영 정책

[업데이트 정책](../adr/0001-update-approval-deadline.md)과 [개발 책임 분리](../adr/0002-separate-analysis-service.md)를 따른다. 기관에 우선 승인·유예 기회를 주고 사전 합의한 기한 후 허용 시간에 자동 적용하는 방향이다. OS·Chrome·GPU 드라이버와 재부팅은 별도 적용 조건을 둔다. 현재 자동 재부팅 금지 계약은 그대로 유지하며, 실제 재부팅 자동화는 후속 명시 설계·수용 전까지 제공하지 않는다.

## 후속 확인

- 분석 서버 배포물의 접근 정책·다운로드 인증과 최초 설치 전달 방식
- OS 설치 자동화·사전 구성 설치 미디어의 첫 배포 포함 여부
- 분석 담당/표시 역할의 설정과 실제 GPU·분석·Chrome 동시 부하 시험
- 서비스 설정·준비 상태·버전·작업 API 계약과 모델/데이터 이전 조건
- 어드민 연동 담당자 협의, 교내 통신 경로·인증과 외부 단절 후 정책 대조
- 구체적인 업데이트 유예 기간·점검 시간·단계적 확대·중단 기준

실제 고객·장비 정보는 이 공개 계획에 넣지 않는다. 모의 설치·합성 데이터 검증과 실제 현장 수용 결과를 구분한다.

## 고정 주소 환경의 최초 연결

사용자가 고정 주소를 PC의 OS에 직접 설정하는 환경이며 GUI에서 직접 설정해도 된다고 설명했다. 기관이 배정한 장비별 주소·프리픽스·게이트웨이·DNS와 SSH는 현장 설치에서 수동 준비하는 것을 첫 구현의 기준 경로로 둔다.

공통 이미지에 실제 장비별 주소를 고정해 복제하지 않는다. 이미지 복원 후 SSH 연결 전에 장비별 네트워크를 준비할 경로가 필요하다. 초기 로컬 적용 절차와 원격 접속 후의 조회·설정은 구분해 설계한다. 이 메모만으로 기존 읽기 전용 네트워크 진단을 원격 네트워크 변경 기능으로 확대하거나 실제 장비의 주소를 변경하지 않는다.

별도로 제안했던 장비 설정 파일 선택 기반의 최초 로컬 네트워크 도우미는 첫 구현 범위에서 제외한다. 공통 이미지 제작 검토는 유지하되 장비별 네트워크 설정은 현장에서 수동 적용한다. ala는 SSH 연결이 준비된 이후 환경·역할·화면·분석 서버 설치와 검사에 집중한다.

## 비공개 배포와 공통 OS 이미지 검토

사용자는 분석 서버를 회사와 설치 기관에만 배포하고자 하며, ala의 공개 배포도 개인 계정을 현장에 남기지 않기 위한 임시 선택이었다고 설명했다. 소스 접근과 배포물 접근을 분리하고 회사가 관리하는 배포 영역에서 기관·장비별 읽기 권한으로 전달하는 방식을 검토한다. 개인 GitHub 로그인이나 개인 토큰을 여러 장비에 공유하는 방식은 전제로 삼지 않는다. 구체적인 배포 서버·레지스트리·등록·자격증명 갱신 방식은 아직 선택하지 않았다.

현행 익명 GitHub 다운로드와 서명 검증·업데이트 경로를 먼저 이전·검증해야 한다. 현재 공개 저장소의 가시성을 변경하거나 이미 게시한 파일·버전을 덮어쓰지 않는다. 비공개 전환이 이미 배포된 사본을 회수하는 것으로 간주하지 않는다.

사용자가 제안한 방식에는 이미 설치·설정한 기준 OS를 이미지로 복제하는 방법도 포함된다. 설치 지시와 패키지 선택을 재실행하는 OS 자동 설치와, 준비된 디스크 상태를 복원하는 공통 이미지 배포는 구분해 검토한다. 후자는 공통 패키지·설정만 포함하고 장비 식별·네트워크·SSH 호스트 키·등록 자격증명·실제 운영 기록은 최초 부팅의 장비별 준비로 분리하는 방향을 제안한다. 실제 고유 정보 초기화·디스크·부트·GPU 호환 검증을 마치기 전에는 검증된 설치 경로로 제공하지 않는다.
