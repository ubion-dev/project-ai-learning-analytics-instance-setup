# ala 화면 관리·자동 업데이트·프론트 갱신 계획

사용자가 승인한 구현 계획이다. 재개 시 AGENTS.md, ala-v1-plan.md,
ala-v1-progress.md와 이 문서를 먼저 읽는다. 구현·자동 검증·실제 GNOME/모니터
수용을 구분한다. 게시 릴리스는 변경하지 않는다.

## 확정 정책

- 기본 TUI: 간편 설정 / 상태 확인 / 화면 관리.
- CLI 정식판은 6시간마다 최대 30분 분산 지연으로 자동 조회·검증·설치한다.
- CLI 갱신으로 현재 Chrome을 종료·재시작·재탐색하지 않는다.
- 화면 관리 코드 변경: 매일 Asia/Seoul 03:00–04:00 대상별 순차 적용.
  놓친 시간은 다음 야간으로 미루며 자동 재부팅하지 않는다.
- 프론트 새 배포 준비 후 실행 중인 창만 순차 갱신한다. 같은 버전 주기 갱신은 없다.
- OS·Chrome RPM·GPU 드라이버는 자동 갱신 대상이 아니다.

## 화면 관리

- 상단은 실제 OS 출력 좌표/크기/복제 배치도, 중앙은 대상별 사이트·실행·사이트
  건강·실제 배치·대기 상태, 하단은 설정·시작·중지·재시작·새로고침·로그.
- 물리/논리 출력·관리 Chrome·확인된 창 수를 분리하며 외부 DID 패널 수는 추정하지 않는다.
- 대상별 ID·URL·출력·자동 시작·프로필·사용자 unit·상태를 분리한다.
- 운영 기본은 논리 모니터당 전체화면 하나. 같은 화면 좌우 분할은 테스트 옵션이다.
- Mutter DisplayConfig로 출력 조회, 전용 GNOME 확장으로 관리 창 식별·배치·재조회.
  출력 부재/모호함은 대기이며 임의 주 화면 이동이나 제목만으로 창 선택하지 않는다.
- 동작 접수와 완료를 구분하고 서비스/프로세스/창/배치/문서 후조건을 검사한다.
  Chrome 정상과 사이트 복구 중을 구분하고 수동 중지 대상을 업데이트로 켜지 않는다.
- 기존 chrome 명령의 기본 대상은 보존하며 --target, reload와 출력/창 JSON 조회 추가.
- schema 1은 메모리에서 기본 대상으로 해석하고 명시 저장에서만 이전한다.
  기존 기본 프로필은 이동·복사·삭제하지 않는다. 작은 터미널에는 목록을 제공한다.

## 버전·동시성

- 설치 CLI / 현재 CLI / 화면별 확정 버전 / 실제 실행 버전 / 후보를 구분한다.
- CLI current와 화면별 확정 release+구성 revision을 분리한다. 장애 재시작/부팅도
  마지막 확정 선택을 사용한다. 기대 구성과 적용 스냅샷도 분리한다.
- 시험 후보는 확정 선택과 별도로 기록한다. 전원 차단 후 마지막 확정 선택을 사용한다.
- 긴 관측 중 root 변경 잠금을 잡지 않는다. 영속 작업 ID·boot ID·generation으로
  예약/commit하며 stop은 generation을 바꿔 적용·복원을 취소한다. 재진입 잠금 금지.
- 실행 경로는 실제 release에 고정하고 실행/확정/후보/복원 참조 release를 보존한다.

## 자동 갱신·야간 적용

- HTTPS·SHA-256·manifest + Sigstore 번들의 고정 저장소/workflow 신원을 검증한다.
  검증기는 전용 환경에 고정한다. 서명 실패는 자동 실행 금지다.
- GitHub 장애/중단/검증 실패에는 기존 버전 유지·제한된 backoff를 적용한다.
- CLI 사전 검사→원자 전환→사후 검사, 실패 시 해당 작업의 포인터만 CAS 복원한다.
- 화면 후보 시작 최대 90초→안정 관측 60초→실패 복원 최대 90초.
  야간 잔여 4분 미만이면 새 대상 시작 금지, 하나 실패하면 나머지 보류.
- 사이트 장애만으로 코드 실패로 판정하지 않는다. 수동 stop은 복원보다 우선한다.
- 공유 GNOME 확장은 구·신 프로토콜 호환을 유지한다. 비호환은 별도 점검 대기다.
- RC20에는 자동 갱신기가 없어 최초 한 번 설치/등록 이전이 필요하다. 표시를 유지하고
  최초 야간 수용 후 자동 운영을 활성화한다. 시험 장비부터 단계적으로 확대한다.
- 중앙 장비 관리 서버는 범위 밖이다.

## 프론트 계약

- 배포 파일: 증가하는 배포 순번·build ID·ready. rollback도 더 큰 순번이다.
  페이지: 실제 build ID와 앱 준비 완료 신호. 배포 파일에는 캐시 방지 정책을 둔다.
- 60초+분산 지연 조회, 같은 새 배포 ready 연속 2회 뒤 후보. 오래된 순번 무시.
- 대상 설정 진입 URL로 한번 갱신→문서+build+ready 확인→성공 뒤 다음 창.
  배포당 대상별 자동 갱신 1회, 실패 시 그 배포의 나머지 보류·명시 재시도 안내.
- 조회 실패는 정상 화면을 바꾸지 않는다. 실제 사이트 오류에는 기존 복구 안내/복귀.
  코드 전환 중 대상의 프론트 갱신은 완료 뒤 처리한다.
- 외부 사이트 HTML/ETag로 배포를 추정하지 않는다. 연동 전 자동 갱신은 꺼짐이다.
- 이 저장소에는 계약/예제/테스트 프론트, 실제 프론트 연동은 해당 프로젝트 별도 작업.
