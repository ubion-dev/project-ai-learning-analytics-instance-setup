# ALA DID 화면 설정 전체 초기화 계획

작성일: 2026-11-06
상태: 로컬 구현·모의 검증 완료, 실제 장비 수용 전. 사용자가 기능 구현을 승인했으며, 실제 장비 초기화와 배포는 별도다.

## 1. 목표와 완료 모습

운영자가 사이트 주소와 화면 배정을 처음부터 다시 잡고 싶을 때, OS 재설치나 간편 설정 전체 재실행 없이 DID 화면 설정만 초기화한다.

화면 관리 → 관리 도구 → DID 전체 초기화 → 변경 대상 확인 → 명시적 승인 → 기존 관리 창 종료 → 모니터별 로컬 안내 화면 → 모니터 식별·사이트 설정으로 이어진다.

완료 상태는 두 단계로 구분한다.

- 서버 처리 완료: 구성과 런타임 선택이 일관되게 확정되고, 안내 문서·관리 창·실제 배치·현재 작업 공간 소속을 확인했다.
- 실기기 수용 완료: 운영자가 각 물리 모니터의 안내 표시를 직접 확인했다. 서버 처리만으로 이 값을 참으로 만들지 않는다.

## 2. 초기화 범위

| 항목 | 정책 |
| --- | --- |
| 사이트 주소 | 모든 새 안내 DID를 `url=None`으로 설정 |
| 모니터 배정·분할 | 검토한 활성 논리 출력마다 전체화면 DID 하나로 재구성 |
| 자동 시작 | 새 안내 구성은 켜짐. 기존 값과 달라지는 대상을 확인창에 표시 |
| 기존 수동 중지 | 승인 시점 이전의 중지는 초기화 대상으로 명시하고 새 안내 시작 의도에 포함. 승인 이후의 중지는 항상 우선 |
| 프론트 연동 | 대상별 연동을 끄고 manifest 주소 등 배포 설정을 비움 |
| 기존 DID 목록 | 연결된 출력에 맞게 재구성. 제거되는 DID는 실행·자동 시작·야간 작업에서 제외 |
| 일반 계정·OS 설정 | 유지. 계정 생성·변경이나 GNOME 정책 재설정을 수행하지 않음 |
| Bash·SSH·Docker·GPU | 유지. 설치·제거·재설정하지 않음 |
| Chrome 프로필 | 삭제·복제·내용 초기화하지 않음. 쿠키·로그인 정보 삭제 기능은 이번 범위 밖 |
| ALA 버전·자동 운영 정책 | 유지. 초기화를 계기로 코드 업데이트·채널 변경·수용 확인 초기화를 하지 않음 |
| 기록·이전 릴리스 | 백업·복구에 필요한 참조를 보존. 자동 삭제하지 않음 |

사이트 설정 초기화는 브라우저 개인정보 삭제와 다르다. 동일 ID의 프로필을 재사용하면 이후 사이트 설정 때 기존 로그인 상태가 남을 수 있음을 확인창과 운영 문서에 명시한다.

## 3. 기존 코드와 연결할 지점

- `ala/display_onboarding.py`: 출력별 안내 후보 생성·로컬 HTML·초기 안내 실행 근거를 재사용한다. 현재 `_eligible`, `_inactive_existing`, `_select_blank`는 기존 사이트·수동 중지를 보호하므로 초기화 목적으로 일반 진입 조건을 완화하지 않는다.
- `ala/runtime.py`: 검증된 선택 스냅샷, 세대 비교, 수동 중지 우선, 서비스 종료·시작·후조건 검사를 재사용한다.
- `ala/screen_swap.py`: 영속 기록, commit 결정 전후 복구, 미완료 작업 격리 원칙을 따른다. 두 대상 교환 기록을 다중 대상 초기화에 억지로 재사용하지 않는다.
- `ala/jobs.py`, `ala/service.py`, `ala/cli.py`: 공통 변경 잠금, root 고정 작업 실행, 요청 검증과 재접속 후 상태 조회에 연결한다.
- `ala/screens_tui.py`: 접힌 관리 도구 진입점, 확인창, 전역 작업 결과와 복구 동선을 추가한다.
- `scripts/build-release.py`: 새 실행 모듈·운영 문서의 배포 포함과 필요한 호환 기능 표기를 검증한다.

신규 `ala/display_reset.py`가 초기화 전용 계획·기록·실행·복구를 맡는 구성을 우선 검토한다. 아래 API는 구현 경로이며 공개 CLI 명령과 구분한다. 기능이 포함된 배포를 설치하기 전 장비에는 제공되지 않는다.

## 4. 읽기 전용 계획과 사전 검사

제안 API는 `screens-reset-preview`, `screens-reset-submit`, `screens-reset-status`, `screens-reset-recover`이다. 조회·화면 진입·크기 변경은 쓰기나 복구를 실행하지 않는다.

미리보기는 다음 자료를 고정하고 만료 가능한 검토 토큰을 반환한다.

1. 저장된 전체 구성 revision, 모든 기존 DID의 확정·후보 선택 및 generation.
2. 관리 서비스·창의 실행 여부와 수동 중지 상태.
3. GNOME의 활성 논리 출력 ID·좌표·해상도·배율·복제·주 출력 정보.
4. 생성·재사용·제거할 DID, 자동 시작 변경, 사라질 사이트·프론트 설정.
5. 사용할 코드의 안내 모드·작업 공간 배치 지원과 실행 중 확장의 기능 지원.

초기화는 활성·잠금 해제된 단일 GNOME 세션과 확정된 출력 목록이 있을 때만 접수한다. 출력 없음·확인 불가·16개 초과는 기존 화면을 유지하고 차단한다. 복제 출력은 논리 출력 하나로 취급한다.

설치·CLI 갱신·대상별 코드/설정 적용·프론트 전환·화면 교환·복구·기존 초기 안내 작업과 겹치면 접수하지 않는다. 런타임 정보나 서비스 소유권을 확인하지 못해도 중지 전에 차단한다.

승인 요청을 받은 서버가 공통 잠금 안에서 토큰·구성·출력·세대·작업 유무를 다시 확인한다. 클라이언트가 보낸 임의 구성이나 경로는 적용하지 않으며 서버가 후보를 계산한다. 검토 이후 바뀌었다면 새 미리보기를 요구한다.

## 5. 새 안내 구성과 코드 선택

- 검토 시점의 주 논리 출력에 `default`, 다른 출력은 기존 초기 안내의 출력 ID 기반 고정 해시 규칙을 사용한다. 번호는 표시용이며 배정 키로 저장하지 않는다.
- 생성 규칙은 공통 순수 함수로 분리해 신규 설치와 초기화의 결과가 다르지 않게 한다. ID 충돌·모호한 출력은 임의 이름 변경 없이 차단한다.
- 모든 후보는 URL 없음, 전체화면, 자동 시작 켜짐, 프론트 비활성이다. DID 외 전역 구성은 그대로 복사한다.
- 재사용 DID의 확정·후보 코드 버전은 유지하되 양쪽 선택의 DID 설정을 함께 새 안내 구성으로 재작성한다. 이전 사이트가 야간 적용으로 되살아나지 않게 한다.
- 새 DID는 검증된 현재 설치 릴리스를 명시적으로 선택한다. 필요한 안내 기능이 없는 재사용 버전은 먼저 코드 적용을 안내하고, 초기화가 몰래 업데이트하지 않는다.
- 제거 DID의 런타임 기록·프로필·릴리스는 복구용으로 보존하지만 활성 대상에서는 제외한다. 로그인·예약 실행이 기록을 직접 열어 오래된 사이트를 다시 시작하지 못하도록 제외 상태를 검사한다.

## 6. 실행과 영속 기록

초기화는 SSH/TUI 종료와 독립적인 root 소유 systemd 작업으로 실행한다. 작업 ID와 고정 실행 경로를 사용하고 일반 사용자 로그인에서 sudo를 호출하지 않는다.

### 실행 순서

1. 공통 잠금 안에서 재검사하고 모든 대상에 대한 영속 작업 기록·예약을 만든다. 부분 예약 실패는 전부 해제하며 Chrome을 중지하지 않는다.
2. 기존 구성·확정/후보 선택·세대·자동 시작 등록·실행/중지 상태와 새 후보를 백업한다. 백업을 재조회해 무결성을 확인한 뒤에만 진행한다.
3. 모든 대상의 로그인 시작·장애 재시작·자동 전환을 초기화 기록으로 격리한다. 구버전 실행 경로가 격리를 지킬 수 없으면 접수를 차단한다.
4. 소유권과 프로세스 증거로 확인한 관리 Chrome만 종료하고 종료 후조건을 검사한다. 하나라도 종료 확인에 실패하면 commit하지 않는다.
5. 새 구성, 대상별 확정/후보 선택, 제외 대상과 자동 시작 등록을 준비한다. 실행 전 충돌은 전체 후보 배정으로 검사한다.
6. 모든 후보와 복구 자료의 준비를 확인한 뒤 root 기록에 commit 결정을 영속 저장한다.
7. commit 이후 새 구성과 모든 대상 상태·등록을 일관되게 확정한다. 일부 파일만 바뀐 동안에는 격리를 유지한다.
8. 격리를 해제할 수 있는 일관성을 확인한 뒤 안내 DID를 시작하고 문서·배치·작업 공간 소속을 재조회한다. 정상적인 안내 모드는 `waiting_configuration`으로 표시한다.
9. 완료와 대상별 결과를 기록하고 더 이상 필요한 예약·임시 작업 등록만 해제한다. 백업과 감사 기록은 보존한다.

오래 걸리는 중지·시작·관측 중에는 공통 잠금을 계속 잡지 않는다. 대신 영속 작업 기록과 세대 기반 예약을 모든 변경 진입점이 확인한다. 시작·안정 관측·복구의 시간 예산은 기존 런타임의 90초·60초·90초 계약을 기준으로 재사용하며 대상 증가 시 전체 작업 상한을 별도로 둔다.

### 기록과 백업

root 소유 전용 디렉터리, 기록·백업 파일 0600, 디렉터리 0700을 사용한다. 실제 사이트 주소가 포함될 수 있으므로 백업·원시 기록을 공개 로그나 PR에 첨부하지 않는다.

기록에는 작업 ID, 시작 boot ID, 실행기 버전/경로, 검토 revision, 대상별 이전·후보 선택, 실행 의도, 예약 세대, 단계, commit 결정, 중지 요청과 결과를 포함한다. 경로·소유권·일반 파일·크기를 검증하고 구성 데이터를 shell/eval로 실행하지 않는다.

## 7. 실패·재부팅·복구 계약

| 상황 | 동작 |
| --- | --- |
| 승인 전 취소·사전 검사 실패 | 구성·서비스·백업 생성 없음 |
| 백업 검증 실패 | 중지하지 않고 실패 표시 |
| commit 전 실패·강제 종료·재부팅 | 전체 이전 배정으로 복구. 원래 실행 중이던 DID만 다시 시작 |
| commit 후 중단 | 전체 새 안내 배정으로 확정을 마무리. 이전 사이트와 새 안내가 섞여 시작하지 않게 격리 유지 |
| 안내 시작·배치 실패 | 새 배정은 유지하고 대상별 실패/확인 불가와 로그·명시 재시도를 제공. 자동 성공 처리나 무한 반복 금지 |
| 세션 잠김·출력 분리 | 현재 단계와 대상 정보를 보존하고 대기·확인 불가 표시. 다른 출력에 임의 재배정하지 않음 |
| 실행 중 수동 중지 | 새 중지 세대가 우선. commit 전에는 전체 취소·복구하되 중지한 DID는 켜지 않음. commit 후에는 새 배정에서 해당 DID 중지 유지 |
| 복구 확인 실패 | 대상별 상태와 복구 필요 표시, 격리 유지. 명시적 복구 재시도만 허용 |

부팅 복구 작업이 일반 DID 시작보다 먼저 미완료 기록을 처리해야 한다. 예약 시간이 만료됐다는 이유로 격리를 해제하지 않는다. 복구 중에도 최신 수동 중지·구성 세대를 오래된 백업으로 덮어쓰지 않는다.

commit 후의 원래 설정 복원은 자동 rollback과 구분한다. 첫 구현에서는 백업 보존과 운영자 안내까지 제공하고, 완료된 초기화를 되돌리는 별도 복원 버튼은 후속 범위로 둔다. 미완료 작업의 commit 전 복구 재시도는 이번 필수 범위다. 재시도는 동일 작업 ID로 이어가고 새 초기화를 중복 생성하지 않는다.

## 8. TUI 흐름

화면 관리의 접힌 **관리 도구** 안에 **DID 전체 초기화**를 둔다. 기존 모니터 클릭·사이트 설정·로그·운영 기능과 메인 버튼 수를 유지한다.

확인창에는 다음을 표시한다.

- 현재 DID 수와 재구성할 논리 모니터 수.
- 각 DID의 현재 주소·출력과 초기화 후 안내 배정. 주소의 인증정보·쿼리·fragment는 기존 표시 보호 규칙에 따라 숨긴다.
- 생성·제외 대상, 자동 시작·수동 중지 변경, 프론트 연동 해제.
- 브라우저 프로필·로그인 정보가 유지된다는 점과 백업 제공 범위.
- 초기화 중 표시가 잠시 중단되며 새 안내를 시작한다는 실행 의도.

기본 포커스는 취소다. 승인 전에는 변경하지 않으며 승인 요청은 한 번만 접수한다. 처리 중 다른 운영 버튼은 작업 상태에 맞춰 비활성화하고, 로그·상태 조회와 수동 중지는 유지한다.

전역 초기화 결과는 선택 DID의 Chrome 실행 결과와 분리한다. 상단에 진행 단계·실패한 대상·다음 행동을 우선 표시한다. 재접속해도 작업 ID로 결과를 찾고, 복구 필요 시 해당 동선을 제공한다.

80×24에서는 요약과 취소/초기화 버튼을 고정하고 변경 대상은 스크롤한다. 120×36에서는 같은 순서로 상세를 확장한다. 키보드만으로 검토·취소·로그·복구·복귀가 가능해야 한다.

## 9. 검증 기준

### 계획·정상 경로

- 미리보기 반복·화면 진입·크기 변경은 파일·백업·서비스 변경 0회.
- 사이트/안내/분할/미배정/연결 해제 DID의 재구성, 출력 1·2·복제·16개·초과를 검사.
- 승인 후 구성·출력·세대 변경은 중지 전에 거부.
- root 권한·소유권 검사, 단일 변경 잠금, 작업 중복 접수 차단.
- 사이트·프론트 설정 제거, 독립 전역 구성·프로필·코드 버전·자동 운영 정책 보존.
- 안내 모드의 외부 사이트/프론트 HTTP 요청 0회. 선택적인 CLI 업데이트 조회와 구분해 측정.

### 실패·경합·중단

- 백업 실패, 부분 예약, 두 번째 이후 대상 중지/시작 실패, 자동 시작 등록 실패.
- 단계별 강제 종료와 commit 직전/직후 재부팅을 모의 검증.
- 수동 중지, 로그인 시작, 장애 재시작, 코드·프론트 갱신, 교환, 다른 SSH의 저장과 경합.
- 제거된 DID의 로그인·야간 실행·오래된 worker가 기존 사이트를 되살리지 않음.
- 출력 연결 변경·세션 잠김·구버전 런타임/확장·손상 기록·복구 실패는 성공으로 추정하지 않음.
- 재접속·재시도·복구 반복으로 중복 DID·작업·시작 요청이 생기지 않음.

### TUI·통합·배포

- 80×24·120×36, 키보드·마우스, 취소 기본 포커스, 긴 목록·한국어 라벨·상태 우선 배치.
- Python 3.12 전체 회귀, Bash·확장 구문, 공개 데이터 검사, 새 모듈/복구 unit의 배포 포함 검사.
- 실제 시험 장비에서 독립 DID 두 개 → 초기화 검토 취소 → 초기화 → 모니터별 안내 → 사이트 재설정 → 재부팅을 확인.
- 실제 Chrome 프로필·일반 사용자 실행·모니터 식별·수동 중지·기존 CLI 보존을 확인.

## 10. 개발 순서와 적용 기준

1. **계획 모델과 보호 조건:** 순수 후보 생성과 읽기 전용 preview, 지원 여부·동시 작업 검사부터 구현한다.
2. **영속 실행·복구:** 백업, 다중 대상 예약·격리, 중지, commit, 부팅 복구와 수동 중지 경합을 구현·검증한다.
3. **안내 실행 연결:** 전용 초기화 경로에서만 기존 안내 생성/실행 근거를 재사용하고 제외 DID 처리·후조건을 확인한다.
4. **TUI 연결:** 사전 검토·기본 취소·접수·재접속·진행·복구·로그 동선을 연결한다.
5. **통합·운영 문서:** 전체 회귀와 실제 시험 장비 수용을 구분해 기록하고 배포 묶음을 검증한다.

구현 완료 후 PR·CI·새 프리릴리스 절차는 별도 작업으로 진행한다. 게시된 RC29와 같은 버전의 자산은 변경하지 않는다. 실제 장비의 초기화는 장비에서 별도로 검토·승인한 요청으로만 실행한다.

## 계획 작성 당시 산출물

계획 작성 당시에는 범위·실행·복구·TUI·검증 기준만 정의했다. 이후 승인된 로컬 구현과 검증 결과는 [진행 기록](ala-v1-progress.md)의 DID 전체 초기화 항목을 따른다. 실제 장비 초기화·PR·배포는 수행하지 않았다.
