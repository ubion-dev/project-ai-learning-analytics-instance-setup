## 상태 조회 시간

상태·계획·검사 API는 독립적인 읽기 전용 검사를 최대 4개 병렬 실행하고, 한 응답 안의 동일 명령·제한 시간·환경 조회를 공유합니다. 다음 조회에는 다시 조사하며 설치 전후 검사와 변경 작업에는 이 조회 캐시를 사용하지 않습니다. 파일/서비스를 바꾸거나 조회 실패를 정상으로 취급하지 않습니다.

초기 화면은 계정과 기존 작업 정보를 먼저 보여주고 전체 검사를 기다립니다. 조회 중 경과 시간을 표시하며, 갱신 중에는 이전 검사 결과임을 명시합니다. 외부 명령·GPU 지원표 요청·그래픽 사용자 RPC의 개별 제한 시간은 유지하므로 모든 장비에서 즉시 완료된다는 보장은 아닙니다.

느린 단계를 확인하려면 `ala status --json`의 `inspection`을 봅니다. `duration_ms`는 관리자 조회 내부 전체 시간이며 `stages`에는 각 검사와 실행 기록·초기 준비 조회 시간이 있습니다. 병렬 실행 때문에 단계 시간의 합은 전체 시간과 다를 수 있습니다. SSH·Python 실행 준비·화면 렌더링 시간은 이 값에 포함되지 않습니다.

세부 항목의 `세부 기록 없음`은 개별 검사/실행 신호가 없다는 뜻입니다. `조회 확인 필요`는 판정 근거를 얻지 못한 경우입니다. 원래 검사 상태와 종료 코드는 유지하며 기록 부재를 정상이나 실행 완료로 추정하지 않습니다.

## 세부 작업 진행 확인

간편 설정 표에서 기능 행을 선택한 뒤 Enter로 세부 항목을 펼칩니다. 큰 기능 옆의 세부 작업 열에는 설치 스크립트가 구조화된 신호로 보고한 현재 작업만 표시합니다. 기본 환경은 패키지, Chrome 설치·정책·실행 명령, 시간대, 시간 동기화로 나뉘고 SSH·Docker·GPU도 실제 스크립트 경계에 맞춰 나뉩니다.

기록의 `substeps`는 stage/id/state/time을 저장하는 추가 필드입니다. 기존 stage 이벤트와 호환되며 이전 실행에 없던 세부 신호를 복원하거나 추측하지 않습니다. 신호가 없는 작업은 구성 항목과 실제 검사 결과만 표시합니다. 재접속 시 기록된 세부 작업을 다시 읽고 최종 불일치·재부팅 대기를 완료보다 우선합니다.

일반 로그의 문장을 상태로 해석하지 않습니다. 고정 프로토콜·허용 식별자·상태만 받아들이며, 진행 기록 오류가 나더라도 실행 중인 RPM 프로세스의 출력을 끝까지 읽은 다음 실패로 보고합니다. 설정 작업이 끝난 뒤 CLI를 갱신합니다.

## 상태와 실행 기록

`ala check`는 저장된 기대 구성을 기준으로 모든 관리 항목을 읽기 전용으로 조사하고 기능별 상태를 요약합니다. 전체 항목과 기대값/현재값은 `ala check --json`으로 확인합니다. 최초 설정 전에는 sudo 실행자의 일반 계정과 기본 구성을 기준으로 조회하며 파일을 만들지 않습니다.
부족한 항목을 자동으로 고치지 않습니다. `ala setup --plan`으로 변경을 확인하고 `--apply`로 반영합니다.
검사에 필요한 도구·권한·네트워크가 없으면 확인 불가로 표시합니다.

설치는 SSH와 독립된 root systemd 작업입니다. TUI 종료나 SSH 접속 종료는 작업 취소가 아닙니다.
재접속 후 `ala runs list`, `ala runs show RUN_ID`, `ala logs --run RUN_ID --follow`로 확인하세요.
전원 차단으로 끝난 작업은 중단 상태로 표시하고 자동 설치 재개하지 않습니다. 다시 계획을 확인한 뒤 적용합니다.
여러 설치나 도구 갱신을 동시에 실행할 수 없습니다.
unit 조회 실패는 실제 작업 중단으로 단정하지 않습니다. 조회 경고가 나면 실행 ID를 보관하고 다시 확인합니다.
화면과 CLI 로그 조회는 최근 128 KiB를 표시하고 원본 전체 로그는 실행 기록 디렉터리에 보관합니다.

## 비대화형 실행과 결과 해석

[구성 예시](../examples/instance.json)의 사용자·주소를 실제 값으로 바꾸고 가져옵니다.

```bash
ala config import ./instance.json
ala config show --json
ala setup --plan --json
ala setup --apply --detach --json
```

`--detach`는 작업을 접수하고 실행 ID를 반환합니다. 성공 응답이 설치 완료를 뜻하지는 않습니다.
`ala runs show RUN_ID --json`과 `ala logs --run RUN_ID --follow`로 최종 결과를 확인합니다.
비TTY 환경에서는 필요한 sudo 인증을 미리 준비해야 합니다. 암호 입력을 무한히 기다리지 않습니다.

- `check`/적용 결과: `0` 정상, `1` 불일치·실패·차단·확인 불가, `2` 적용/입력 대기.
- 명령 사용 오류: `64`.
- 계획 조회는 변경이 필요해도 계획 계산에 성공하면 `0`입니다.
- GPU 없음은 해당 없음, 새 드라이버의 재부팅 필요는 대기입니다. 실행 기록은 실제 현재 상태를 대신하지 않습니다.

기능을 꺼도 기존 패키지를 자동 삭제하거나 과거 설정을 일괄 복원하지 않습니다.

이 도구의 백업은 전체 OS·DB 백업이 아닙니다. 패키지 제거·전체 롤백 기능은 제공하지 않습니다.

## 적용 대기

- NVIDIA 신규 설치: 유지보수 시간에 재부팅 후 같은 구성을 다시 적용해 컨테이너 GPU 연결을 준비합니다.
- 공식 펌웨어·커널 모듈 보완: 사용 중 드라이버를 다시 로드하지 않습니다. 재부팅 후 `ala check`로 연결 상태를 다시 확인합니다.
- Docker 저장 설정과 현재 데몬 차이: 작업 영향을 확인하고 유지보수 시간에 재시작/재부팅합니다.
- GNOME/GDM/logind 설정: 기존 세션을 강제로 종료하지 않습니다. 유지보수 재부팅 후 검사합니다.
- URL 없음: 구성에서 URL을 저장하고 다시 적용합니다. 예제 주소를 자동으로 띄우지 않습니다.

도구는 진행 중 RPM 트랜잭션을 죽이거나 예약된 오프라인 업데이트를 임의 삭제하지 않습니다.
Podman/runc, 기존 고장 GPU, Secure Boot 서명, 관리 외 Chrome 정책 충돌은 원인부터 해결해야 합니다.

## 화면 복구

표시용 Chrome은 일반 사용자 supervisor가 관리합니다. 시작 전·실행 중 HTTP 검사와 관리하는 주 문서의 응답/실패를 구분해서 감시하며, 정상 화면을 주기적으로 재탐색하지 않습니다. 시작 시 사이트가 준비되지 않았거나 장애가 확인되면 네트워크에 의존하지 않는 복구 안내를 표시합니다. 장애 후 복구가 확인되면 관리 탭만 원래 URL로 이동합니다.

기본 HTTP 검사는 30초 간격·요청 제한 5초입니다. 연속 실패 3회로 장애를 판정하고 연속 성공 2회로 복구를 확인합니다. 관리 주 문서의 HTTP 오류/탐색 실패는 별도로 처리하며 하위 이미지·아이콘 하나의 실패를 전체 화면 장애로 보지 않습니다. TLS 검증은 유지합니다. 상태는 `ala chrome check`와 TUI의 표시 사이트 감시 항목에서 확인합니다.

### 안내 없이 페이지가 다시 로딩될 때

Chrome 프로세스 재시작, ala의 탭 탐색 명령, 브라우저에서 발생한 새 문서 이동을 구분합니다. 정상 HTTP 확인은 페이지를 탐색하거나 새로고침하지 않습니다. 외부 페이지의 JavaScript/meta 새로고침을 ala가 임의 차단하지 않습니다. PID가 같다는 사실만으로 ala의 탭 재탐색까지 배제할 수는 없습니다.

화면 관리(c)의 상세에서 실행 중 감시 버전과 탐색 횟수를 확인합니다. `ala chrome status --json`의 `health.navigation`도 같은 기록입니다.

- `display_requests`: 이 감시가 보낸 원래 표시 주소의 탐색 요청 수.
- `recovery_requests`: 이 감시가 보낸 로컬 복구 안내 탐색 요청 수.
- `browser_navigations`: 위 명령과 연결되지 않은 새 주 문서 이동의 관측 수. 페이지 코드·사용자 입력·브라우저 동작 중 원인을 확정한 값이 아닙니다.
- `last_command`, `last_browser_navigation`, `last_error`: 마지막 명령/관측/오류의 고정 범주와 시각. 주소·문서 제목·스크립트·스택은 기록하지 않습니다.

횟수는 현재 감독 프로세스가 시작된 뒤의 기록이며, 브라우저의 모든 화면 갱신이나 부분 콘텐츠 변경을 세지 않습니다. 명령 요청 수가 그대로인데 브라우저 문서 이동만 증가했다면 해당 재탐색을 ala가 직접 요청한 근거는 없습니다. 양쪽 모두 그대로면 실제 문서 새로고침이 아닌 페이지 내부 콘텐츠 갱신일 수도 있습니다.

CLI만 갱신하면 실행 중인 감독 프로세스는 이전 코드로 유지됩니다. `health.supervisor_version`과 탐색 기록이 없으면 0회로 추정하지 않습니다. 새 진단을 적용하려면 표시 중단이 가능한 시점에 화면 관리에서 한 번 명시적으로 재시작한 뒤 관측합니다. 설치·업데이트가 대신 재시작하지 않습니다.

HTTP 성공은 앱 데이터 갱신·로그인·JavaScript 렌더링까지 검증한 결과가 아닙니다. HTTP 확인과 실제 탐색 사이의 상태 변화로 오류 화면이 잠깐 노출될 가능성도 있습니다. 이 기능은 장애 화면에 고착되지 않도록 복구하는 범위이며, 오류 픽셀이 한순간도 표시되지 않는다는 보장이 아닙니다. 실제 표시 내용 수용과 앱별 heartbeat는 별도로 확인합니다.

기존에 실행 중인 Chrome은 도구 갱신만으로 강제 재시작하지 않습니다. 감시를 적용하지 않은 기존 실행은 전환 대기로 표시하며, 명시적인 화면 재시작 또는 다음 그래픽 로그인에서 supervisor로 전환합니다. 제어는 표시용 프로필과 자식 프로세스에 한정하고 네트워크 디버깅 포트는 열지 않습니다.

간편 설정은 기본 환경과 화면 정책을 확인한 뒤 GDM/Chrome 등록을 준비하고 Docker/GPU를 진행합니다. Docker/GPU 차단 때문에 화면 등록이 누락되지 않게 하며, 현재 Chrome은 시작·중지·재시작하지 않습니다. 현재 세션·Chrome·사이트의 상태는 전체 검사와 화면 관리에서 따로 관측합니다.

RC17부터 설정 계획/적용 결과는 화면의 등록 준비를 검사합니다. 현재 Chrome이 중지됐거나 그래픽 로그인이 없다는 이유로 설정 완료를 실패로 바꾸지 않습니다. GPU 재부팅 등 다른 설치 조건과 URL 입력 대기는 그대로 표시합니다. `ala status --json`의 최상위 results는 전체 관측이고 configuration_report는 같은 검사 패스의 설정 결과입니다. 설정 plan/apply 결과는 scope=configuration으로 구분합니다.

TUI의 화면 관리 버튼 또는 c에서 현재 표시 서비스를 시작·중지·재시작하고 상태·로그를 확인합니다. 시작 요청을 접수한 뒤 실제 서비스·사이트 상태를 별도로 재조회하며 접수만으로 화면 정상을 표시하지 않습니다. 간편 설정과 관리 작업은 기존 변경 잠금을 공유합니다. GDM이나 현재 세션을 강제로 재시작하지 않습니다.

RC14 이하의 버전 경로가 들어간 관리 unit/desktop 파일은 RC15에서 간편 설정을 한 번 실행하면 백업 후 고정 진입점으로 이전합니다. 등록은 `/usr/local/bin/ala`를 사용하므로 실행 경로의 버전 차이만으로 생기던 불일치를 방지합니다. 도구 업데이트 자체가 OS 설정을 적용하지는 않습니다.

표시 계정의 GNOME 세션 하나를 사용합니다. user manager가 존재하는 것과 그래픽 로그인이 있는 것은 다릅니다.
관리 계정과 표시 계정이 다를 수 있으며, Chrome은 항상 표시 계정 권한으로 실행합니다.
새 서비스는 `ala-chrome.service`, 기존 관리 서비스는 `did-chrome.service`입니다.
기존 서비스는 설치 적용만으로 강제 종료하지 않습니다. 명시적 `ala chrome restart`나 다음 그래픽 로그인에서 전환합니다.

URL 응답 준비를 기다리며 기동 재시도합니다. TLS 검증 오류를 우회하지 않습니다.
Chrome 반복 장애는 시작 제한에 걸릴 수 있습니다. 로그로 원인을 확인하고 `ala chrome restart`로 재시도합니다.
`stop`은 현재 실행만 중지합니다. 자동 시작이 켜져 있으면 간편 설정을 재실행해도 현재 중지 상태는 유지하고 다음 그래픽 로그인에서 시작합니다. 이후 로그인에도 중지하려면 자동 실행을 구성에서 끄고 적용하세요.

부팅 복구는 GDM 부팅 등록·graphical.target·자동 로그인 계정·첫 실행 안내 완료·GNOME autostart의 _session·표시용 user service의 _runtime-dispatch와 확정된 _chrome-run 및 재시작 정책을 함께 준비합니다. 이 파일/등록 검사는 실제 재부팅 수용을 대신하지 않습니다. BIOS 전원 복구와 부팅 전 디스크 암호는 관리 범위 밖입니다.

Chromium은 자기 PID를 별도 systemd scope로 옮길 수 있습니다. cgroup 문자열이 다르다는 이유만으로 무관 프로세스로 판단하지 않고 부팅·직접 PPid·UID·양쪽 시작 식별자·표시 프로필과 실제 인자를 대조합니다. 증거가 불명확하면 Chrome/health를 확인 불가로 표시하고 임의 프로세스를 제어하지 않습니다. [Chromium 구현](https://chromium.googlesource.com/chromium/src/+/refs/tags/138.0.7186.0/components/dbus/xdg/systemd.cc)

Linux Chromium은 `/proc`에 원래 NUL 구분 인자 대신 옵션을 공백으로 합친 프로세스 제목을 표시할 수 있습니다. ala는 공식 stable 실행 파일(`/opt/google/chrome/chrome`)과 지원하는 제목 형식을 확인한 뒤 프로필·필수 옵션·금지 옵션을 검사합니다. 이 제목은 원래 인자의 경계를 보존하지 않으므로 공백·인용 부호 등으로 해석이 모호하면 옵션별 누락 오류 대신 프로세스 확인 불가로 남깁니다. [Chromium 제목 구현](https://raw.githubusercontent.com/chromium/chromium/main/base/process/set_process_title.cc)

RC17 이하에서 이 형식 때문에 모든 옵션이 누락으로 표시된 경우 먼저 ala를 갱신하고 다시 검사하세요. 도구 갱신은 현재 Chrome을 재시작하지 않습니다. 실제 옵션 불일치나 감시 전환이 남은 경우에만 화면 관리에서 다음 조치를 선택합니다.

### 부팅 뒤 Chrome이 뜨지 않을 때

자동 로그인·Chrome 등록 파일 일치와 실제 부팅 실행은 별도로 확인합니다. GNOME 로그인 진입점은 사용자 서비스 시작을 한 번 요청하고, 실제 그래픽 세션/화면 환경의 준비 대기는 그 서비스 안에서 최대 45초 동안 수행합니다. Chrome 제어 연결과 관리 탭의 초기 준비도 최대 30초 안에서 확인합니다. 시작 요청 접수는 실제 화면 표시 성공을 뜻하지 않습니다.

동일 로그인 진입점이 다시 호출돼도 이미 실행 중인 표시 서비스를 재시작하지 않습니다. 일반 시작에 실패 초기화를 선행하지 않고, 실패/시작 제한은 명시적인 화면 재시작으로만 초기화합니다. 로그아웃이나 화면 중지는 준비 대기 중인 서비스도 종료합니다. 세션 종료·교체로 취소되면 전용 종료 코드와 unit 정책이 이를 정상 취소로 처리하며 자동 재시작하지 않습니다.

화면 관리의 로그에서 `[ala-autostart]` 단계와 Chrome 서비스 결과를 확인합니다. 사용자 저널 파일을 읽지 못하면 관리자 RPC가 동일 화면 계정 UID에 해당하는 고정 서비스·부팅 진입점의 시스템 저널로 조회를 보완합니다. 다른 사용자나 전체 환경 로그를 읽어 표시하지 않습니다.

`ExecMainStartTimestampMonotonic=0`·`Result=success`만으로 해당 부팅에서 실행한 적이 없거나 성공했다고 결론내리지 않습니다. systemd가 종료된 unit의 상태를 정리한 뒤 다시 로드하면 기본값을 볼 수 있으므로 현재 상태와 부팅 로그를 함께 확인합니다. [systemd 상태·정리 설명](https://www.freedesktop.org/software/systemd/man/257/systemctl.html)

CLI 갱신은 GDM·현재 Chrome을 재시작하지 않습니다. RC20은 취소 전용 unit 정책도 보완하므로 기존 설치는 도구 갱신 뒤 간편 설정을 한 번 적용합니다. 이후 다음 정상 GNOME 로그인에 새 진입점과 정책이 적용됩니다. 실제 장비는 재부팅 후 SSH로 다시 접속하고 Chrome 표시와 모니터 화면을 관찰해야 수용 완료입니다.

무인 표시용 `--password-store=basic`은 키링을 쓰는 보관 방식보다 보호가 약합니다.
표시 프로필에는 계정·암호·토큰을 입력하지 않습니다. 다른 Chrome 프로세스의 저장 방식은 변경하지 않습니다.

## 업데이트 결과와 작업별 검사

업데이트 실행 기록은 `/var/lib/ala/updates/`에 저장합니다. 접수·다운로드·체크섬·manifest·설치·재검사를 구분하고 실제 설치 버전이 대상과 일치해야 완료로 판정합니다. `ala update --status [--run RUN_ID] [--json]`은 기록과 현재 상태를 읽기만 하며, unit 조회 실패나 중단을 성공으로 바꾸지 않습니다.

GitHub 장애·API 제한·DNS·TLS·다운로드 오류는 갱신 실패로 표시합니다. 실패 뒤 현재 설치 버전을 확인해 기존 버전이 유지됐는지 구분하며, 조회할 수 없으면 확인 불가로 남깁니다. 진행 중/완료된 결과는 GitHub API의 현재 가용성과 독립적으로 조회합니다.

검사는 각 작업이 의존하는 대상을 기준으로 합니다. 로컬 상태 조회가 GitHub 접속 실패 때문에 차단되지는 않습니다. 설치/설정은 기존 현재 상태 조사·적용 전 확인·적용 후 재검사를 유지합니다. 지속 감시는 표시 서비스와 사이트에 적용하며 OS 패키지·GPU·네트워크를 주기적으로 재설치하거나 강제 재시작하지 않습니다.
페이지의 카메라/마이크 권한, 사이트 자체 팝업, 콘텐츠 오류와 지속적인 장애 감시는 별도입니다.

## 업데이트와 보안 설정

DNF Automatic·PackageKit과 GNOME 업데이트 경로를 차단합니다. 별도 cron/관리 에이전트/Flatpak 업데이트까지 차단했다고 간주하지 않습니다.
`ala setup`에는 전체 OS 업그레이드가 없습니다. 초기 설치도 새 부팅 커널·Rocky release/repository/key 패키지를 의존성으로 설치하려 하면 중단합니다.
일반 라이브러리 등 필요한 의존성의 변경까지 차단하거나 현재 OS 전체를 고정하는 정책은 아닙니다.
분리 전 Bash 진입점의 `--upgrade`는 명시적으로 선택한 경우에만 전체 DNF 업그레이드를 수행합니다. `ala`는 이 옵션을 전달하지 않습니다.
Chrome 내부 구성요소/확장 업데이트는 RPM 업데이트와 별개이며 기본 동작을 유지합니다.
점검 시간의 수동 DNF 업데이트는 가능합니다. 전체 OS 업데이트·Chrome 업데이트 후 호환성/재부팅/화면을 다시 확인하세요.
ala 최초 설치는 명시적으로 진행합니다. 이후 서명·현재 배포·실기기 수용 확인을 마치고 자동 운영을 켜면 정식 CLI와 야간 화면 코드 갱신을 분리해 수행합니다. [업데이트 정책](UPDATES.md)을 따릅니다.

장치 자동 준비는 별도 선택 없이 `ala setup --plan`에 나타나고 `ala setup --apply`에 포함됩니다.
PCI/USB 정보와 기존 드라이버 연결을 조사하며, 검증된 공식 패키지의 누락만 보완합니다.
인터넷 단절을 곧바로 드라이버 고장으로 판단하지 않습니다. Wi-Fi 자동 연결·DNS·라우팅은 별도 상태 확인이 필요합니다.
구체적인 지원 범위와 대기·차단 해석은 [드라이버 정책](DRIVERS.md)을 참고하세요.

BIOS 전원 복구, 디스크 암호 입력, 앱 컨테이너 restart 정책과 DB 영속화는 별도입니다.


## 초기 OS 준비와 바탕화면 자동 로그인

`ala prepare --plan/--apply`는 최초 공식 OS 업데이트를 위한 별도 작업입니다. 자동 재부팅·자동 재개하지 않습니다.
`ala status`의 preparation 결과와 `ala runs`에서 상태를 확인합니다. 완료 후 재실행은 OS 업데이트를 반복하지 않습니다.
초기 준비 중 설치되는 패키지의 스크립트는 서비스를 재시작할 수 있으므로 운영 중 정기 업데이트용으로 사용하지 않습니다.
단계별 설명은 [초기 준비](PREPARATION.md)를 따르세요.

자동 로그인은 계정 비밀번호를 삭제하는 방식이 아닙니다. GDM에서 지정한 일반 사용자로 로그인합니다.
`display.configuration`은 구성 준비, `display.session`과 `display.session_lock`은 현재 로컬 세션/잠금 힌트입니다.
URL 미입력 또는 Chrome 자동 실행 off는 바탕화면 자동 로그인을 끄지 않습니다.
`display.visual_acceptance`는 실제 화면 관찰이 자동 검사 범위 밖임을 표시합니다. 모든 설정이 맞아도 실제 화면 확인은 별도입니다.
로그인 화면·잠금 화면·GDM 또는 그래픽 초기화 장애는 서로 다른 상태로 진단합니다. GDM을 강제 재시작하지 않습니다.

## 기본 설정 흐름

`ala`와 `ala tui`는 간편 설정 / 상태 확인 / 화면 관리 / DID 빠른 점검 탭을 제공합니다. 간편 설정 실행 버튼 한 번으로 저장된 구성이나 최초 기본값을 적용합니다. sudo 인증은 대화형 시작에서 처리합니다. 처음 적용할 때는 실행자의 일반 계정과 기본값을 공통 변경 잠금 안에서 저장합니다. 저장된 구성이 있으면 보존하며, 상태·계획 조회는 구성 파일을 만들지 않습니다. root 직접 접속으로 일반 계정을 알 수 없으면 먼저 `ala config edit` 또는 구성 가져오기로 지정해야 합니다.

각 화면의 위쪽에서 **현재 상태와 다음 조치**를 확인합니다. 아래 목록에서 항목이나 DID를
선택하면 근거와 상세 결과를 볼 수 있습니다. 업데이트(`u`)와 자동 운영에도 같은 순서를
사용합니다.

설치 엔진은 모듈별로 현재 상태를 재확인합니다. Podman 충돌이 있으면 Docker와 이후 GPU 단계는 중단되며, 앞서 준비한 화면/Chrome 등록은 유지됩니다. 충돌 해결 후 간편 설정을 다시 실행하면 현재 상태를 재검사하고 필요한 작업을 진행합니다. 마지막에 모든 항목이 완료됐다고 표시하지 않으며 `ala check`에서 원인과 다음 조치를 확인합니다. Podman은 일반 사용자와 root 각각 `podman ps -a`, `podman volume ls`로 기존 사용 여부를 확인한 뒤 정리하세요.

일반 텍스트 콘솔은 `ala console`로 선택합니다. 개별 옵션 변경은 `ala config edit`에서 가능합니다. `ala check --json`은 요약되지 않은 전체 기대값·현재값을 반환합니다. 실행 중 작업은 `ala status`, 중단한 터미널에서 재접속한 뒤 기록은 `ala runs list`로 조회합니다.

### Bash 자동 제안·구문 강조

간편 설정에서 **Bash 자동 제안·구문 강조 설치**를 선택하고 실행하면, 일반 운영 계정에
고정 버전의 `ble.sh`를 설치합니다. 체크는 해당 설치 작업에만 적용됩니다. 설치 후 다시
체크하지 않아도, 다음 대화형 SSH 로그인부터 계속 사용할 수 있습니다. 기존 Oh My Bash
프롬프트와 Tab 완성을 사용하며, 비대화형 SSH 명령에서는 이 기능을 로드하지 않습니다.
Bash 편의 기능 설치 시 사용자 설정이 없으면 자동 제안을 배경색 없이 회색 글자로 표시합니다.
RC24에서 설치한 계정도 RC25의 Bash 편의 기능 설치기를 다시 실행하면 이 스타일을 적용할 수 있습니다.

설치 시 기존 `~/.bashrc`는 `~/.bashrc.ala-backup.*`에 백업합니다. 설치에 실패하면 작업
결과에서 **Bash 자동 제안·구문 강조** 세부 항목과 로그를 확인하고, 옵션을 다시 선택해
재시도합니다. 선택 기능 실패 이후에도 기존 환경과 DID 설정 단계는 계속 진행됩니다.

## Podman 설치 감지로 중단된 경우

Docker 공식 RHEL 설치 안내는 Podman을 사전 정리 대상으로 명시합니다.
간편 설정 실행 시 Podman 충돌이 있으면 사용 여부를 조회하고 확인 창을 엽니다.
root와 홈 디렉터리가 있는 일반 로컬 계정, 컨테이너 저장소나 설정이 있는 시스템 계정에서
컨테이너·볼륨·이미지·pod·사용자 정의 네트워크를 확인합니다. Quadlet 자동 실행 설정이
발견되거나 어느 계정에서든 조회에 실패하면 정리 승인을 비활성화하고 이유를 표시합니다.

조회 기준으로 미사용이면 DNF가 계산한 제거 예정 패키지 전체를 확인 창에 표시합니다.
기본 선택은 취소입니다. **제거 후 설정 계속**을 선택하면 승인 정보를 해당 설치 작업에
기록하고, 공통 변경 잠금 안의 백그라운드 작업이 제거 직전에 사용 여부와 제거 목록을
재확인합니다. 목록 변경·사용 흔적·조회 실패·제거 실패 시 Docker 설치를 중단하고
실행 기록과 로그에 남깁니다. 정리에 성공하면 기존 Docker 설치 단계로 이어집니다.
점검과 설치 중에는 다른 터미널에서 Podman 작업을 시작하지 마세요.
Podman 이외의 충돌 패키지는 기존 진단에 따라 별도로 해결합니다.

CLI 설치 또는 수동 점검이 필요한 경우 ala를 종료한 일반 사용자 SSH 터미널에서 확인합니다.

```bash
podman ps -a
podman volume ls
sudo podman ps -a
sudo podman volume ls
```

조회 오류를 빈 목록으로 취급하지 마세요. 일반 계정의 rootless 저장소는 root 조회에 나타나지 않으므로 다른 사용 계정도 있다면 별도로 확인해야 합니다. Podman을 사용하지 않는 초기 장비이고 필요한 데이터·다른 계정·예약 서비스가 없음을 확인한 경우 `sudo dnf remove podman`으로 제거 예정 목록을 검토한 뒤 진행합니다. `-y`로 검토를 건너뛰지 않습니다. 정리 후 ala에서 간편 설정을 다시 실행합니다.

근거: [Docker RHEL 설치](https://docs.docker.com/engine/install/rhel/), [Podman rootless 설명](https://docs.podman.io/en/latest/markdown/podman.1.html#rootless-mode). 공개 검사에 Podman 공식 문서 호스트를 추가한 근거이기도 합니다.

### DID 빠른 점검

재부팅 후 화면이 보이지 않으면 **DID 빠른 점검**을 열고 대상이 여러 개면 DID를 선택합니다.
GNOME 세션, Chrome, 창 배치, 사이트 로드 중 먼저 확인할 단계와 다음 조치를 표시합니다.
이번 부팅 로그는 선택한 DID의 Chrome 서비스로 범위를 좁힙니다. GNOME 로그인 문제는
같은 부팅의 GDM 서비스 상태와 로그 단서만 요약합니다. 시작·재시작은 대상 확인 후 요청하고
다시 점검합니다. 서버 점검을 통과해도 실제 DID 표시와 패널 입력은 현장에서 확인합니다.
